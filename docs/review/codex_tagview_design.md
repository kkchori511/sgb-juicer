# ‘태그별 기록’ 설계안 UX 검토

- 검토일: 2026-11-09
- 대상: `docs/design/TAG_VIEW.md` v0.16 초안과 현재 작업 트리의 기록·태그 관련 코드
- 기준 상태: `feature/v0.15`, HEAD `9680e3d`. 검토 시작부터 코드·문서에 기존 미커밋 변경이 있었으며 이를 보존했다. 줄 번호는 검토 당시 작업 트리 기준이다.
- 범위: 설계 검토다. 새 화면의 구현·실기 동작을 검증한 보고서가 아니다. Chrome·앱 GUI 실행, 외부 전송, 코드 수정, git commit/push는 하지 않았다.

## 전체 의견

**태그 선택 → 여러 학생의 관련 기록 확인 → 같은 자리에서 수정**이라는 방향은 요구에 맞는다. 마감 기록을 함께 보여주되 읽기 전용으로 두고, 선택 태그를 뺀 기록이 즉시 사라지지 않게 하는 점도 좋다. AI·최종안 편집을 새 화면에 추가하지 않는 범위는 유지하는 편이 좋다.

구현 전에는 **반·수업 필터의 의미, 기록별 이동 대상, 여러 기록의 저장 보장, 저장 후 되돌리기**를 먼저 확정해야 한다. 모두 여러 담당의 자료를 한 화면에서 바로 고치게 되면서 생기는 위험이다. 기존의 한 학생·한 담당용 화면과 저장 함수를 그대로 재사용한다고 해결되지는 않는다.

기본 배치는 **학년-반 → 학생 → 담당·항목별 기록**을 추천한다. 태그는 한 개만 고르고, 다른 태그 기록은 처음부터 함께 불러오지 않는다. 미정 세 가지의 구체적인 결정은 T15~T17에 적었다.

심각도 **상**은 잘못된 자료 수정·덮어쓰기·편집 손실 위험, **중**은 범위·상태 오인과 반복 작업, **하**는 탐색·설명 개선이다. 아래 항목은 설계상 미정 사항 및 기존 코드 재사용 시 주의점이며, 아직 없는 새 화면의 버그로 단정하지 않았다.

## 상세 검토

### T01. 반·수업 필터가 ‘학생 범위’인지 ‘기록 범위’인지 모호함

- **심각도: 상**
- **문제:** 설계 `TAG_VIEW.md:39–41`대로 기록마다 수업 또는 학년-반을 부여하면, ‘2학년 3반’을 선택했을 때 2학년 3반 학생의 세특 기록 중 수업명이 있는 기록만 빠질 수 있다. 교사는 자기 반 학생의 독서 기록 전부를 보고 있다고 생각하기 쉽다. 또한 현재 `groupOf`는 과목에 수업이 하나라도 있으면 미지정 학생을 ‘수업 미지정’으로 묶는다(`app.js:1635–1639`). 설계의 ‘수업 없으면 학년-반’과 같지 않다. `groupOf`는 현재 담당 전역 상태를 참조하므로 여러 담당을 섞는 새 화면에 그대로 적용할 수도 없다.
- **제안:** 필터의 두 종류를 명시적으로 구분한다. **‘학년-반: 2학년 3반’은 해당 학생들의 모든 허용 항목 기록을 조회**, **‘수업: 공통수학1·1학기·A반’은 그 담당·수업의 기록만 조회**하도록 정한다. 한 선택창 안에서도 ‘학년-반 / 과목별 수업’ 구역을 나누고 선택 결과 설명을 붙인다. 수업 식별은 이름만 쓰지 않고 담당·학기를 포함해 동명 A반을 구분한다. 미지정 수업의 처리도 기존 화면과 한 규칙으로 맞춘다.

### T02. 학생 카드의 ‘항목별 기록에서 열기’는 한 곳으로 정할 수 없음

- **심각도: 상**
- **문제:** 한 학생 카드에 진로·자율·수학·동아리 기록이 함께 들어가는데 학생 머리에는 이동 버튼이 하나다(`TAG_VIEW.md:19–26`, `49`). 어느 담당으로 가는지 불명확하다. 마감 해제도 학생 전체가 아니라 `group_id × item × student_no` 단위다(`records.py:119–125`). 학생 카드 하나를 파랗게 표시하거나 학생 단위로 이동하면 다른 항목을 해제·수정할 수 있다. 기존 `sourceLabel()`은 ‘직접 입력/인박스에서/다른 항목에서 이동’이라는 유입 경로 표시이므로 담당 출처 배지를 대신하지 못한다(`app.js:1846–1850`).
- **제안:** 각 기록 또는 같은 담당의 기록 소그룹에 **`[진로 · 2학년 3반 · 연간] [그 항목에서 열기 ↗]`**를 둔다. 세특은 과목명·학기, 동아리는 담당명을 항상 표시한다. ‘수업 A반’은 담당명 뒤의 보조 정보로 분리한다. 링크는 해당 기록이 보이는 위치까지 이동시키고, 돌아오면 태그·필터·펼침·스크롤·작업 위치를 복원한다. 마감은 기록의 담당 범위마다 표시하고 `수학1 마감 해제 안내`처럼 대상을 명확히 한다.

### T03. 기존 leaveOk만 붙이면 여러 기록의 미저장 내용을 보호하지 못함

- **심각도: 상**
- **문제:** 설계는 칸 이탈·Ctrl+S 저장과 `leaveOk` 재사용을 약속한다(`TAG_VIEW.md:53–55`). 현재 `leaveOk`는 확인창이 아니라 최종안·대기 설정 저장을 실행하고 실패하면 이동을 막는 함수다(`app.js:92–102`). 새 화면의 여러 기록 초안을 자동으로 알고 있지 않다. 단순 blur 저장은 요청 중 다음 필터로 이동하거나, 같은 기록에 두 저장이 겹칠 때 오래된 글이 나중에 반영될 수 있다. `update_record`는 수정 시각 비교 없이 전달된 필드를 덮어쓰며, API 응답도 갱신된 기록 없이 성공만 반환한다(`records.py:398–429`, `api.py:639–642`).
- **제안:** 학년도·기록 ID별로 초안, 저장된 값, 저장 중 여부, 실패 상태를 관리하고 같은 기록의 요청은 순서대로 처리한다. **내용과 태그 등 실제 바뀐 필드만 저장**해 오래된 전체 카드 값으로 다른 수정분을 덮지 않는다. 태그·필터·묶음 접기·페이지 추가·메뉴·학년도 변경은 저장 대기와 진행 중 요청까지 확인한 뒤 반영한다. 실패하면 초안과 현재 화면을 보존하고 `다시 저장 / 내용 복사`를 제공한다. Ctrl+S는 이 화면의 변경 기록 전체 저장으로 정하고 `전체 저장 중 2건 / 저장 실패 1건`을 상단에도 보여준다. 다른 경로에서 바뀐 기록은 조용히 덮지 않도록 변경 여부 확인도 필요하다.

### T04. ‘바로 고치기’에 저장 후 되돌리기 정의가 없음

- **심각도: 상**
- **문제:** 자동 저장이므로 다른 학생 칸을 잘못 클릭해 붙여넣은 내용도 blur로 확정된다. 설계의 되돌리기는 선택 태그를 뺀 경우에만 있다(`TAG_VIEW.md:57`). 기존 `update_record`는 수동 수정 이전 내용을 보관하지 않는다. `original`은 AI 후보를 기록에 반영할 때 처음 원문을 보존하는 별도 기능이며 수동 수정 이력이 아니다(`records.py:398–429`, `431–443`). 브라우저 Ctrl+Z만으로는 다른 칸·화면 이동 뒤의 복구를 보장할 수 없다.
- **제안:** 본문·날짜·활동명 변경과 태그 변경 모두 **저장 전 초안 취소 / 저장 후 직전 변경 되돌리기**를 구분한다. 저장 전 값과 적용 후 값을 보관하고, 이후 추가 수정·마감이 있으면 오래된 되돌리기로 덮지 않도록 막거나 비교하게 한다. 일괄 태그 변경은 실행 단위로 원래의 태그 포함 여부를 보관한다. 되돌리기가 준비되지 않는다면 첫 버전은 기록별 `저장 / 수정 취소`를 보이는 방식이 더 안전하다. 매 저장마다 확인창을 띄우는 방식은 피한다.

### T05. 마감 기록은 본문만 잠그면 안 되며 일괄 태그 작업도 영향을 받음

- **심각도: 중**
- **문제:** 설계는 마감 기록의 ‘글상자 읽기 전용’을 명시하지만 날짜·활동명·태그 칩·체크박스까지 잠그는지는 불분명하다. 기존 `update_record`는 태그만 바꿔도 마감을 검사하고, `tag_records`는 선택한 기록 중 마감 기록이 하나라도 있으면 적용 전에 거부한다(`records.py:232–248`, `398–400`). 마감 포함이 기본인 새 화면에서 쉽게 겪게 된다. 한 학생의 일부 항목만 마감될 수도 있다.
- **제안:** 마감 기록은 내용·메타정보·태그 변경을 모두 잠그고 일괄 작업용 체크박스도 비활성화한다. 조회·복사는 허용한다. `현재 결과 23건: 수정 가능 18건·마감 5건`을 보여주고 선택은 수정 가능한 기록에 한정한다. 실행 중 마감 상태가 바뀌어 거부된 경우에는 선택·초안을 보존하고 이유를 설명한다. 새 화면에서 자동 마감 해제를 제공하지 않는 설계는 유지한다.

### T06. 태그를 뺀 뒤 화면에 남는 기록과 실제 개수의 관계가 미정

- **심각도: 중**
- **문제:** 선택 태그를 빼도 흐리게 남기는 방향은 좋지만 언제 사라지는지, 그 기록을 계속 편집·일괄 선택할 수 있는지, ‘태그 없음’에 태그를 더했을 때도 같은 규칙인지 정해져 있지 않다. 일괄 제거는 여러 학생 카드를 동시에 바꾼다. 기존 `update_record(tag_ids)`는 전체 태그 목록 교체이고 `tag_records`는 추가/제거 작업이다. 반대 작업을 무조건 실행하는 되돌리기는 원래 태그가 없던 기록에 새 태그를 붙이는 실수를 만들 수 있다.
- **제안:** 저장 성공한 뒤 `독서 태그를 뺐습니다 · 목록에서 제외 예정 [되돌리기]`로 남기고 **같은 조회 결과를 보는 동안 위치를 보존**한다. 본문을 흐리게 만들어 읽기 어렵게 하기보다 제외 예정 배지를 쓴다. 다음 조회/필터 적용 시 정리하되 안내한다. ‘태그 없음’에서 추가한 경우도 대칭적으로 처리한다. 집계는 실제 저장값 기준으로 갱신하고 `제외 예정 2건 화면에 남음`을 따로 표시한다. 되돌리기는 원래 포함 상태를 복원하고, ‘이 기록에서 태그 빼기’와 ‘태그 사전 삭제’를 분리한다.

### T07. 처음 100건만 표시하면 ‘전부’와 일괄 선택의 범위가 어긋남

- **심각도: 중**
- **문제:** 기록 100건이 학생·담당의 중간에서 끊기면 같은 학생의 나머지 기록이 없는 것처럼 보일 수 있다(`TAG_VIEW.md:60`). 접어도 이미 만든 글상자와 초안 상태가 줄어드는 것은 아니다. 전체 선택·선택 유지 범위가 미정이면 필터 밖의 숨은 기록까지 태그를 바꾸거나, 반대로 보이는 일부만 고치고 끝냈다고 생각할 수 있다.
- **제안:** 모든 해당 학생을 한 목록에서 찾아갈 수 있게 하되 첫 표시량과 전체 결과는 구분한다. 예: `전체 340건·92명 / 현재 100건 표시`. 학생 카드가 잘리면 `이 학생 기록 8건 중 3건 표시 [나머지 5건]`를 표시한다. 버튼은 `전체 결과 중 다음 100건 보기`처럼 구체화한다. 선택은 기록 ID 기준으로 관리하고 기본은 **현재 표시된 수정 가능 기록만 선택**한다. 필터·태그 변경 때는 선택 해제를 알리고, 전체 결과 선택은 첫 버전에서 생략하는 편이 안전하다. 일괄 작업에는 학생 수와 기록 수를 함께 표시한다.

### T08. 기록이 있는 학생만 나오는 화면에서 ‘미입력’을 판정할 수 없음

- **심각도: 중**
- **문제:** 태그 기록이 있는 학생만 조회하므로 그 학생·항목은 이미 기록이 있다. 기존 `status_map`도 기록이나 후보가 있으면 ‘입력 중’으로 본다(`records.py:130–156`). 따라서 이 화면에 안 보이는 학생이 미입력인지, 다른 태그만 있는지, 필터에서 제외됐는지 알 수 없다. ‘태그 없음 40’이나 ‘협업 0’을 회색으로 보인다고 생기부 미입력 40명/0명이라는 뜻은 아니다. 설계의 ‘상태’ 필터도 실제로는 마감 포함 여부만 고르는 기능이다.
- **제안:** `선택 태그의 기록만 표시합니다. 이 목록은 학생별 미입력 현황이 아닙니다`를 짧게 설명한다. 태그 수는 항상 ‘건’으로 표시한다. 기본 상태 필터는 `마감 포함 여부`로 명명하거나, 실제 상태 필터로 확장한다면 `입력 중 / 최종안 있음 / 마감`을 제공한다. 재검토 필요는 별도 조건이다. 학생 전체 미입력 확인은 현황판/항목별 기록으로 연결하고 태그 화면에 빈 학생 카드를 자동 생성하지 않는다.

### T09. 상태·선택·저장 성공·묶음색을 같은 색으로 읽게 해서는 안 됨

- **심각도: 중**
- **문제:** 설계는 네 상태 색과 GROUP_COLORS 재사용을 정하지만 실제 배치 위치·적용 범위는 미정이다. 현재 작업 트리는 상태 색을 회색·노랑·초록·파랑으로 쓰고, 일반 선택은 중립색 `--sel`로 구분하도록 보완되어 있다(`style.css:610–627`). 반면 기록 체크 선택에는 여전히 초록 테두리·배경이 사용된다(`style.css:492–508`). 이것을 재사용하면 선택한 ‘입력 중’ 기록도 완료처럼 보인다. 그룹 팔레트에도 회색·청록 계열이 있으므로 색의 완전 분리보다 표시 역할 분리가 중요하다.
- **제안:** 아래 표처럼 **상태 배지는 기록의 담당별로 고정 위치**, 선택은 체크·중립 외곽선, 저장은 독립 문구, 묶음은 작은 장식 띠로 정한다. ‘저장됨’의 초록 체크가 ‘최종안 있음’을 의미하지 않게 한다. 마감 파랑은 기록 배지에만, 학생 카드 전체에는 적용하지 않는다. 색 외에도 기호·글자를 항상 함께 둔다. 새 화면과 기존 항목별 화면의 `STATUS` 의미를 일치시킨다.

| 의미 | 태그별 기록 권장 표시 | 혼동 방지 |
|---|---|---|
| 미입력/기록 없음 | 공통 범례의 회색 ○, 필요하면 현황판 링크 | 기록이 있는 본 목록에 억지로 회색 상태를 만들지 않음 |
| 입력 중 | 노랑 ◐ `입력 중` | 글상자 저장 중과 다른 상태 |
| 입력 완료 | 초록 ◑ `최종안 있음` | 단순 기록 저장 성공과 구별 |
| 마감 | 파랑 ● `마감·읽기 전용` | 학생 전체가 아니라 해당 담당·항목 상태 |
| 최종안 재검토 | 기존 상태 옆 노랑 ! `기록 수정 후 최종안 확인 필요` | 초록 상태를 노랑으로 통째로 교체하지 않음 |
| 선택한 태그·기록 | 체크/선택됨 + 중립색 외곽선 | 완료 초록·마감 파랑과 분리 |
| 저장 상태 | `수정 중 / 저장 중 / 저장됨 / 저장 실패·다시 저장` | 실패를 미입력 회색으로 표현하지 않음 |
| 반·수업 묶음 | 이름 + 작은 색 띠 | 띠는 반 식별이며 작업 상태가 아님 |

### T10. 기록 수정이 최종안에 바로 반영되는 것처럼 보일 수 있음

- **심각도: 중**
- **문제:** 태그 화면에서 표현을 맞춰도 실제로 바뀌는 것은 원자료 기록이다. 최종안 문장은 별도로 남는다. 설계의 stale 안내는 적절하지만 ‘학생에게 최종안이 있으면’이라고만 되어 있어 다른 담당의 최종안도 경고 대상으로 오해할 수 있다. 기존 로직은 **같은 담당·항목·학생의 내용이 달라졌을 때만** stale을 표시하며 날짜·활동명·태그만 바꾸면 표시하지 않는다(`records.py:424–429`). API 성공 응답에는 stale·최종안 정보도 없다.
- **제안:** 화면에 `기록을 수정하는 화면입니다. 최종안 문장은 자동으로 바뀌지 않습니다`를 명시한다. 저장 후 해당 담당만 `최종안 확인 필요 [그 최종안 확인]`으로 안내하고 기록/학생/담당별 중복 경고는 묶는다. 메타정보 변경도 재검토 사유로 볼지는 별도 결정한다. 현재 로직을 유지한다면 내용 수정과 태그 정리를 동일하게 경고한다고 약속하지 않는다. 저장 응답이나 후속 조회에서 실제 상태를 확인한 뒤 배지를 갱신한다. 바이트 수는 개별 기록의 길이로 표시하고, 여러 담당이 섞인 화면에서 현재 선택된 한 담당의 최종안 목표를 모든 기록에 공통 적용하지 않는다.

### T11. 실시간 필터·집계·정렬 갱신이 편집 중 위치를 흔들 수 있음

- **심각도: 중**
- **문제:** 태그 수는 반·항목 필터만 반영한다고 적힌 부분과 ‘필터 반영’이라는 API 설명이 혼재한다(`TAG_VIEW.md:33`, `72`). 마감·검색·비활성 옵션을 포함하는지 불명확하다. 검색어가 포함된 문장을 고치면 일치 조건을 벗어나 즉시 사라질 수도 있다. 태그 변경이나 내용 검색 후 목록을 다시 그리면 커서·스크롤·선택이 바뀔 수 있다. 필터 선택지를 현재 태그 결과에서만 만들면 결과가 0이 된 선택값도 사라질 위험이 있다. 기존 `tags()`의 used는 학년도 전체 기록 기준이라 그대로 표시할 수 없다(`records.py:159–170`).
- **제안:** 태그별 수는 **현재 태그 선택을 제외한 다른 필터 전체**를 적용한 기록 수로 정의하고, 학생 수는 학번 중복 제거한 인원으로 센다. 한 기록에 여러 태그가 있으므로 태그 수의 합은 전체 기록 수가 아님을 전제로 한다. 편집 시작 후에는 해당 행의 위치를 유지하고 저장 완료 후에도 조건 이탈 표지만 보여준다. 사용자가 조회 조건을 바꿀 때 목록을 정리한다. 옵션은 학년도·접근 가능한 담당 범위에서 안정적으로 제공하고 현재 0건인 선택도 유지한다. 정렬 기준은 명시하고 수정 시각순 자동 이동은 피한다.

### T12. 비활성·보관 학년도·역할에 대한 편집 정책이 부족함

- **심각도: 중**
- **문제:** ‘비활성 포함’일 때 편집도 허용하는지 정해져 있지 않다. 비활성은 학생 전역 속성이 아니라 담당 소속별 상태여서 같은 학생의 다른 과목은 활성일 수 있다. 현재 `update_record`는 마감을 확인하지만 활성 여부는 별도 차단하지 않는다. API는 보관 학년도 쓰기를 막으나 `update_record(rid,data)`에는 기대 학년도 인자가 없다(`api.py:584–592`, `639–642`). 여러 초안을 들고 학년도를 넘기는 새 화면은 맥락을 더 엄격히 보존해야 한다. 비담임 역할에 숨긴 자료와 비활성 자료도 다른 개념이다.
- **제안:** 기본은 해당 기록의 담당 소속이 활성인 것만 조회한다. ‘비활성 포함’은 처음에는 **조회·복사만 허용**하고 소속별 비활성 배지·명렬 이동을 제공하는 편이 안전하다. 보관 학년도는 모든 변경·되돌리기를 비활성화한다. 역할·담당 범위는 서버 조회·집계에도 동일하게 적용한다. 기억한 태그·필터·초안·저장 요청은 학년도 단위로 구분하고, 학년도 전환 전에 저장을 끝내거나 전환을 막는다. 되돌아왔을 때 삭제·이름 변경된 태그의 복구 경로도 안내한다.

### T13. 긴 목록에서는 학생·담당·작업 버튼이 화면에서 사라짐

- **심각도: 하**
- **문제:** 모든 본문을 큰 글상자로 펼치면 학생 한 명이 화면 여러 장을 차지할 수 있다. 작은 Windows 창에서 반·항목·상태·검색을 한 줄에 넣으면 화면 높이도 많이 쓴다. 스크롤 중인 본문이 누구의 어느 과목인지 놓치면 바로 고치기의 장점이 사라진다. [더 보기]라는 표현도 메타정보 펼침과 다음 기록 표시 양쪽에 쓰인다.
- **제안:** 좁은 창에서는 태그 목록을 상단 `태그: 독서 ▼` 선택기로 접고 필터를 두 줄로 배치한다. 필터·검색·저장 요약은 상단에, 학생명·담당은 편집 중 쉽게 확인되는 머리에 남긴다. 본문은 기본 3~5줄에서 필요할 때 늘리고 페이지 전체 스크롤을 주로 사용한다. 버튼은 `날짜·활동명 수정`과 `다음 100건 보기`로 구분한다. 학생·기록 간 Tab 이동과 Ctrl+S의 초점 복귀도 정한다.

### T14. 기존 ‘태그’ 메뉴와 새 ‘태그별 기록’의 차이를 설명해야 함

- **심각도: 하**
- **문제:** 기존 사이드바의 ‘태그’는 태그 사전을 관리하고, 새 화면은 기록을 고른다(`index.html:37–43`). 둘 다 같은 아이콘·비슷한 이름이면 교사가 원하는 화면을 찾기 어렵다. 기존 `delete_tag`는 마감과 관계없이 사전과 연결을 전체 정리하는 별도 동작이다(`records.py:222–230`). 기록 칩의 ×와 같은 의미로 보이면 위험하다.
- **제안:** 새 메뉴 위치는 요구대로 항목별 기록 바로 아래에 두고, 기존 메뉴를 `태그 관리`로 설명한다. 새 화면은 `태그로 기록 모아 수정`, 관리 화면은 `태그 이름 추가·변경·삭제`라는 역할 안내를 둔다. 새 화면의 [+]는 기존 태그 선택을 기본으로 하고 관리 이동을 별도로 제공한다. 기록 칩 ×의 접근성 이름/도움말은 `이 기록에서 독서 태그만 빼기`로 구체화한다.

### T15. 미정 ①: 첫 버전은 ‘학년-반 → 학생’ 기본, 보기 토글은 보류 권장

- **심각도: 중**
- **문제:** ‘반·수업 → 학생’에서 기록별 수업을 그룹 기준으로 삼으면 같은 학생이 여러 그룹에 반복된다. 여기에 담당별 보기까지 추가하면 학생 수·선택·저장·되돌리기·복귀 위치를 두 방식에서 일치시켜야 한다. 항목별 기록은 이미 담당 중심 탐색을 제공하므로 초기에 두 모드를 모두 넣을 이득이 확실하지 않다.
- **제안:** **전체 보기의 기본은 학생의 학년-반 → 학생 → 담당·항목별 기록**으로 고정한다. 수업 필터를 선택했을 때는 해당 담당·수업 학생만 보여주고 원래 학년-반을 학생 머리에 남긴다. 한 학생 안의 기록은 담당·학기별로 모으고 각 담당 안에서는 기존 저장 순서를 따른다. 담당 필터로 대부분의 과목 중심 작업을 해결하고, 실제로 ‘과목별 표현 비교’ 수요가 확인되면 보기 토글을 추가한다. 그룹별 학생 수를 더한 값과 전체 고유 학생 수는 구분한다.

### T16. 미정 ②: 태그 한 개 선택 유지, AND/OR는 이번 버전에서 제외 권장

- **심각도: 하**
- **문제:** 다중 선택에는 ‘독서와 탐구 모두 / 둘 중 하나’뿐 아니라 ‘태그 없음과 다른 태그 동시 선택’, 포함/제외, 선택 태그 제거 뒤 잔류 조건이 추가된다. 초보 교사가 결과를 예측하기 어려워지고 왼쪽 기록 수의 의미도 복잡해진다.
- **제안:** **이번에는 단일 태그 선택을 유지**한다. `독서 기록 중 2학년 3반·세특`처럼 나머지 필터를 조합해 범위를 좁히고 왼쪽에 태그 찾기를 제공한다. 나중에 추가한다면 기본 선택을 복잡하게 만들지 말고 별도 `조건 더하기`에서 `모두 포함 / 하나라도 포함`을 글자로 명시한다. ‘태그 없음’은 다른 태그와 배타적인 조회로 둔다.

### T17. 미정 ③: 다른 태그 기록은 기본 숨김, 필요할 때 읽기 전용 참고

- **심각도: 하**
- **문제:** 다른 기록까지 자동으로 함께 가져오면 선택 태그의 결과·건수·일괄 선택 범위가 흐려진다. 교사는 독서 기록을 고친다고 생각하다 다른 기록을 수정할 수 있다. 현재 요구의 핵심은 관련 기록 전부를 바로 수정하는 것이므로 전체 학생 기록을 기본으로 섞을 필요는 없다.
- **제안:** **초기 기본 화면에는 표시하지 않는다.** 필요하면 학생 카드에 `다른 기록 참고`를 두어 누를 때 읽기 전용으로 불러온다. 참고 영역에는 담당·태그·참고용 배지를 붙이고 본 목록의 건수·선택·저장 대상에 포함하지 않는다. 수정하려면 해당 태그/항목별 기록으로 명시적으로 이동하게 한다. 참고 기능이 없더라도 T02의 기록별 이동과 돌아오기만 갖추면 첫 버전 사용은 가능하다.

```text
└──────────────┴────────────────────────────────────────┘
선택 2명 3건 [태그 더하기] [태그 빼기]  ※ 수정 가능 기록만 선택
```

첫 진입은 현재 학년도의 기억한 태그, 반·항목 전체, 마감 포함, 활성 소속 기준을 권한다. 기억한 태그가 없으면 첫 태그를 임의로 고르기보다 선택 안내를 보인다. 0건 화면은 `이 태그 자체가 0건 / 필터 때문에 0건 / 비활성만 있음 / 접근 가능한 담당 없음`을 구분하고 가능한 해제 버튼을 제공한다. ‘전체’는 현재 학년도·역할로 볼 수 있는 담당 전체라는 점을 안내한다.

## 구현 전 결정 및 검증 시나리오

결정 우선순위는 T01~T04, T05~T12, 탐색 편의 순이다. 검토 중 코드를 바꾸거나 테스트용 데이터를 만들지는 않았다. 다음은 새 화면 구현 후 확인할 시나리오다.

- 같은 학생이 진로·두 과목·동아리에 같은 태그를 가질 때 학년-반 필터는 빠짐없이, 수업 필터는 해당 담당만 보여주는지
- 서로 다른 과목의 ‘A반’, 수업 미지정 학생, 한 담당만 비활성인 학생이 올바르게 구분되는지
- 내용 수정 직후 태그 제거·필터 변경·마감 해제 화면 이동·학년도 변경을 연속 수행해도 초안이 보존되는지
- 저장 응답 지연·실패·다른 경로 수정 때 오래된 내용이 덮어쓰지 않고, 실패 기록으로 돌아갈 수 있는지
- 내용/태그를 되돌릴 때 그 뒤 수정·마감된 자료를 덮지 않고 원래 포함 상태만 복원하는지
- 마감 기록이 섞인 100건 이상 목록에서 학생별 잔여 기록·선택 범위·전체 수를 정확히 알 수 있는지
- ‘태그 없음’에서 태그 추가, 선택 태그 제거, 내용 검색어 삭제 뒤 기록이 사라지거나 편집 커서가 이동하지 않는지
- 좁은 Windows 창·125%/150% 배율·키보드만으로 학생/출처/저장 상태를 확인하며 수정할 수 있는지
