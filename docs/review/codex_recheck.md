## 검토 방법

- `codex_request_recheck.md`, 1차 보고서, `fixes_v0.8.md`, 최신 요구사항을 읽고 `40f0bdb..9c44a6e`의 코드 차이와 현재 코드를 대조했다.
- 1차와 같은 합성 자료·임시 데이터 폴더를 사용했다. 변경된 `scan.pdf_path(year, bid)` 서명 등은 새 코드에 맞추되 재현 의미는 유지했다.
- Python은 실제 API·DB·파일 처리 코드를 호출했다. OpenRouter/CLOVA/다운로드는 모의 처리하고 실제 네트워크 요청과 브라우저 열기를 차단했다. OS 클립보드 쓰기도 모의 처리했다.
- JS는 현재 `app.js`에서 해당 함수를 읽어 Node의 모의 DOM/API와 함께 실행했다. 응답/저장 처리 순서 및 실패를 제어했다. Chrome이나 pywebview 화면을 띄우지는 않았다.
- 백업 실패는 임시 폴더에서 `shutil.copytree` 또는 `shutil.move`에 오류를 주입했다. 실제 exe를 바꾸거나 실행하지 않았다. 단일 실행 잠금은 Python 자식 프로세스로 로컬 파일 잠금만 시험했다.
- `PYTHONDONTWRITEBYTECODE=1`로 실행했다. 프로젝트 코드·테스트·다른 문서는 수정하지 않았고 이 결과 파일만 작성했다.

## 2. 새 문제와 남은 출시 차단 항목

### N01. 늦은 자동 저장이 최신 수정 또는 채택한 후보를 덮어씀

- **판정:** 새 문제(H12 수정으로 도입)
- **우선순위 / 분류:** 높음 / 자료·버그

- **근거·재현:** 최종안이 없는 학생으로 실제 `renderFinal()`을 실행하고 직접 작성 후 flush를 성공시켰다. DB 역할의 모의 저장에는 글이 존재했지만 마감 버튼과 다듬기 버튼은 모두 disabled=True였다. 버튼 상태가 처음의 `f === null`에 고정되고 flush는 R.view/상태/버튼을 갱신하지 않는다.
- **문제:** 교사는 ‘저장됨’을 보지만 바로 마감하지 못한다. 다시 학생을 선택하면 풀리는 우회가 있으나 정상 순차 흐름은 아니다. 반대로 기존 글을 모두 지워 DB 최종안이 삭제된 경우에는 오래된 f 기준으로 버튼이 켜져 있을 수 있다.
- **고치는 방안:** 저장 성공 응답으로 최종안 존재·텍스트·상태를 동기화하고 관련 버튼을 갱신한다. 입력 중 글을 덮어쓰는 전체 재렌더링 대신 현재 입력 버전과 일치하는 최소 상태 갱신을 사용한다.

## 4. 수정 후 우선 확인할 수용 조건

1. **저장 순서:** 느린 자동 저장이 있는 동안 최신 수정·후보 채택·마감을 실행해도 마지막 사용자의 의도만 남고, UI와 DB가 일치해야 한다.
2. **전환 실패:** 저장 실패 시 다음 학생/항목/학년도/종료로 진행하지 않으며, 실패 초안이 남아 재시도할 수 있어야 한다. 저장 요청에는 학년도가 있어야 한다.
3. **백업 게시:** DB 사본만 있고 스캔 복사가 실패한 백업은 일반 복원 대상으로 노출·사용되지 않아야 한다.
4. **복원 교체:** 학년도 DB/PDF 교체의 각 지점에서 실패를 주입해도 전체 이전 상태 또는 전체 복원 상태 중 하나로 돌아가야 한다.
5. **되돌리기:** 내용 외 필드·후보·잠금이 변경돼도 무조건 삭제하지 않으며, 검사 뒤 새 변경이 끼어들지 않아야 한다.
6. **작업 배제:** AI 먼저/유지보수 먼저 양쪽 순서에서 충돌을 막고, AI 작업 등록은 DB 저장 완료까지 살아 있어야 한다.
7. **잠금 양도 실패:** 다운로드 뒤 교체/실행이 실패해도 살아 있는 기존 앱이 무잠금으로 자료를 계속 쓰지 않아야 한다.
8. **직접 작성:** 빈 최종안부터 작성해 자동 저장한 뒤 다른 학생을 다시 선택하지 않고 바로 다듬기·마감할 수 있어야 한다.
