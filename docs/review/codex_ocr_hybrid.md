# OCR 하이브리드 추가분 검토

검토일: 2026-11-22. 로컬 `feature/ocr-hybrid`의 `f0b5e0d`를 `feature/v0.19`와 비교했다. 요청서에 적힌 커밋 4개와 계획의 결정 1~7을 대상으로 했다. 검토 시 작업 트리의 `app`, `tests`는 검토 브랜치와 같았다.

**현재 상태로 합치기는 보류를 권한다.** 머리글 가림·개인정보 제거, PDF 렌더링의 스레드 안전성부터 고쳐야 한다. 정상 결과 재사용과 검토 저장에도 아래 재현되는 문제가 있다. 원본 PDF와 엔진 결과가 있어 복구 가능한 경우도 있지만, 화면에서 고른 결과·학생 경계가 조용히 달라지는 것은 막아야 한다.

## 검토·시험 방법

- 코드·시험 파일을 `/private/tmp/ocr-hybrid-review/snapshot`에 복사해 실행했다. 자료 폴더는 임시 폴더로 분리했다.
- `sitecustomize` 감사 훅으로 소켓 연결·DNS 조회·외부 송신을 차단하고, 브라우저 열기와 Chrome·curl 등의 실행도 막았다. OCR·AI 호출 재현은 가짜 함수/응답으로만 했다. 실제 API, Chrome, 웹 요청, 외부 전송은 하지 않았다.
- 요청한 `.venv/bin/python tests/run_all.py`에 해당하는 전체 시험을 복사본에서 실행: **47/48 파일 통과**, 약 33초. `test_ocr_hybrid.py`는 통과했다.
- 실패한 `test_records.py`는 `pbcopy`가 종료 코드 1로 실패한 환경 문제였다. OS 클립보드 쓰기만 가짜 함수로 대체해 재실행했을 때 통과했고, 내보내기 문자열 생성도 확인했다. 전체 시험이 무조건 통과했다고 계산하지 않았다.
- `node --check app/web/app.js` 통과. 브라우저 대신 Node VM에서 실제 `showDiffReview`, `showOriginal` 함수를 추출해 최소 DOM과 지연 응답으로 상태 문제를 재현했다. 이는 실제 화면의 배치·키보드 시험을 대신하지 않는다.
- 보조 재현: `/private/tmp/ocr-hybrid-review/probes.py`, `probes_extra.py`, `ui_probe.cjs`. 실행 결과와 전체 시험 로그도 같은 임시 폴더에 있다. 이 스크립트들은 앱 코드 수정 없이 메모리에서만 함수를 대체한다.

## 높은 심각도

### H1. PDFium을 여러 스레드에서 동시에 호출한다

- **파일:줄:** `app/api.py:3029`, `app/api.py:3043`, `app/ocr_vision.py:64`, `app/ocr_vision.py:67`.
- **근거:** Qwen 작업자 3개가 각자 `render_png` → `PdfDocument` → `render`를 실행한다. `store_lock`은 저장만 보호하며 PDFium 호출에는 적용되지 않는다. 설치된 `pypdfium2-5.15.1.dist-info/METADATA:939`는 “Incompatibility with Threading” 절에서 PDFium이 스레드 안전하지 않다고 명시한다. 서로 다른 문서 객체를 만드는 것으로 해결되지 않는다.
- **영향:** 여러 쪽을 읽을 때 네이티브 라이브러리 충돌·프로세스 종료 위험이 있다. Python 예외 처리로 복구되지 않는 종류다. 기존 하이브리드 시험은 병렬 경로의 렌더링을 가짜 함수로 바꾸므로 이 위험을 검증하지 못한다. 실제 충돌을 유발하는 부하 시험은 하지 않았다.
- **고칠 방향:** PDFium의 문서 열기·렌더링·닫기를 직렬화하고, PNG 생성이 끝난 뒤 네트워크 요청만 병렬화한다. 원본 보기·가림 미리보기·확대 자르기도 같은 보호를 쓰거나 별도 프로세스로 격리한다.

### H2. 하이브리드에서는 가림 0%를 동의 없이 허용한다

- **파일:줄:** `app/api.py:2977`, `app/api.py:2978`, `app/inbox.py:642`, `app/web/app.js:7838`, `app/web/app.js:7895`.
- **재현:** `ocr_ai_consent=False`인 새 묶음에서 `inbox_scan_ocr(bid, 1, "hybrid", {"mask": 0})`. 성공을 반환하고 두 쪽의 가짜 렌더러 모두 `mask=0.0`으로 호출됐다. 실제 그림을 보내지는 않았다.
- **영향:** UI의 가림 슬라이더와 설정은 0을 허용한다. 동의 검사는 `mode == "ai"`에만 있어, 하이브리드에서는 이름·학번을 가리지 않은 그림을 보내려 한다. 화면의 “흰색으로 가린 이미지” 안내와도 다르다.
- **고칠 방향:** 하이브리드는 유효한 양수 가림을 필수로 하거나, 가림 없는 전송을 명시적으로 동의받는 정책을 적용한다. 요청 옵션만 검사하지 말고 저장된 `ai.mask`를 포함한 **실제로 렌더링할 값**을 검증한다. 음수·비정상 수치도 함께 거부한다.

### H3. AI 제안의 개인정보 제거가 차이 경계에서 깨진다

- **파일:줄:** `app/inbox.py:732`, `app/inbox.py:737`, `app/ocr_compare.py:267`, `app/api.py:3114`.
- **재현:** 명렬에 `가나다 / 10399`가 있을 때 전체 문자열은 `○○ ○○`로 지워진다. 그러나 차이가 이름 가운데에 있으면 `before="내 이름은 가"`, `clova="나"`, `after="다입니다."`가 각각 검사되어 그대로 전송용 문자열에 남는다. 학번도 `before="학번: 103"`, 후보 `9`, `after="9 이름: 마바사"`로 쪼개지면 제거되지 않는다. 명렬 밖의 이름 `마바사`도 그대로 남는다.
- **영향:** 후보와 문맥을 이어 읽으면 이름·학번을 복원할 수 있다. 가림 영역 밖의 글이나 OCR 오독 때문에 신원 부분이 차이가 될 때 특히 문제다. `strip_ids`를 사용하는 계획과 달리, 현재 보정 경로는 명렬의 완전 일치 정규식만 각 조각에 적용한다.
- **고칠 방향:** 각 엔진의 원문에서 먼저 신원 구간을 찾고, 그 구간과 겹치는 후보·문맥을 가린 뒤 분할한다. `scan.extract_ids`/`strip_ids`가 처리하는 라벨·학번·명렬 밖 머리글 이름도 반영한다. 임의의 본문 이름까지 완전 탐지한다고 보장하지 말고, 남는 한계는 전송 확인에 정확히 적는다.

## 중간 심각도

### M1. CLOVA 페이지 실패 시 정상 Qwen 결과를 쓰지 않는다

### M2. 실패 뒤 저장된 정상 결과만으로 마무리할 수 없다

- **파일:줄:** `app/inbox.py:607`, `app/inbox.py:631`, `app/api.py:2996`, `app/api.py:3050`.
- **재현:** 하이브리드에서 CLOVA만 예외, Qwen 2쪽은 성공하도록 했다. `sc.ocr=None` 상태에서 Qwen만으로 다시 시작하면 `{ok: True, clova: False, ai_pages: 0}`이지만 끝난 뒤에도 `sc.ocr=None`이다. 추가 Qwen 호출은 0회였다.
- **원인·영향:** 최종 글 갱신은 `scan_store` 안에서만 일어난다. 모드 변경 뒤 실행할 엔진이 하나도 없으면 저장·갱신 없이 완료 이벤트만 보낸다. 정상 Qwen 결과를 이미 받은 사용자가 시작 화면에서 벗어나지 못한다. CLOVA 결과만 남은 중지 묶음에서도 같은 구조다.
- **고칠 방향:** 모드를 바꿀 때 또는 실행 종료 시 현재 캐시로 최종 글을 갱신한다. 전체 엔진 실패와 부분 성공을 구분해, 정상 결과 사용·실패한 쪽 재시도를 선택할 수 있게 한다.

### M3. CLOVA 중지·뒤쪽 실패 때 앞서 읽은 구간을 버려 재호출한다

- **고칠 방향:** CLOVA도 구간/쪽별 원 결과와 완료 상태를 응답마다 저장한다. 미완료·실패 쪽만 재시도하고, 중지 전에 받은 응답은 보존한다. 기존 묶음 호환과 구간별 페이지 번호를 시험한다.

### M4. ℃의 일부만 다른 경우 원문 치환 범위가 잘못된다

- **파일:줄:** `app/ocr_compare.py:29`, `app/ocr_compare.py:35`, `app/ocr_compare.py:185`.
- **재현:** CLOVA `100℃`, Qwen `100°F`. 비교에서 `℃`를 `°C`로 펼친 뒤, 차이를 `CLOVA: ℃ / Qwen: F`로 만든다. Qwen을 고르면 **`100F`**가 된다. 기대값은 `100°F`다. 이 예는 `big=False`다.
- **영향:** 표시된 후보도 실제 Qwen 원문의 의미 있는 단위 범위와 다르고, 선택 후 기호가 유실된다. `℃ == °C`만 확인하는 현재 시험으로는 발견되지 않는다.
- **고칠 방향:** 하나의 원문 글자를 여러 비교 글자로 펼칠 때 그 글자 전체에 대응하는 양쪽 범위를 확보한다. 동등화 토큰을 원자적으로 취급하고, 겹치는 원문 치환은 병합한다.

### M7. 차이 검토를 닫으면 미확정 학생 경계·페이지 빼기가 초기화된다

- **파일:줄:** `app/web/app.js:7731`, `app/web/app.js:7910`.
- **재현:** 페이지 묶기에서 학생 경계를 바꾸고 한 쪽을 뺀 뒤 차이 검토 창을 열었다 닫는다. 닫기 함수는 `SC.starts=null`로 만들고 `loadBatch()`를 부른다. 이후 `renderScan`이 저장된 `sc.starts`, `sc.skipped`로 두 값을 다시 채운다. Node 재현에서도 닫은 즉시 `starts`가 `null`로 바뀌는 것을 확인했다.

- **고칠 방향:** 같은 PDF의 검토·편집 후에는 현재 경계와 제외 상태를 보존한다. 새 PDF나 명시적인 초기화 때만 버린다. 묶음 ID/원본 버전과 화면 상태를 함께 관리한다.

### M8. 페이지 응답 순서가 뒤집히면 다른 쪽에 선택을 저장한다

- **재현:** 실제 함수를 Node VM에서 실행했다. 1쪽→2쪽→1쪽으로 이동하고 마지막 1쪽 응답을 먼저, 이전 2쪽 응답을 나중에 돌려줬다. 화면 제목은 **1쪽**, 후보는 **2쪽**으로 그려졌다. 그 상태의 Qwen 선택은 `inbox_scan_decide(..., page=0, ...)`으로 보내졌다.
- **영향:** 오래된 후보를 보고 고른 선택이 현재 쪽의 같은 `d0` 등에 적용된다. 원본 이미지 요청도 공유 변수 `cur`를 사용해 잘못된 조합을 보일 수 있다.
- **고칠 방향:** 요청 시 페이지 번호·요청 세대를 고정하고 최신 페이지와 일치하는 응답만 그린다. 저장은 `r.page`에 묶고, 이동 중/저장 중 상태와 응답 순서를 관리한다. AI 제안을 기다리며 이동하는 경로도 같은 검사를 한다.

### M9. 새 낱말을 만들어도 ‘새로 만든 글자’ 경고가 나오지 않는다

- **파일:줄:** `app/ocr_compare.py:279`, `app/ocr_compare.py:280`, `app/web/app.js:8001`.
- **재현:** 두 후보가 `가나다`, `라마바`이고 합친 제안이 `바나나`일 때 `parse_fix`는 `new=False`를 반환한다.
- **원인·영향:** 글자 집합 포함 여부만 검사해 순서·횟수·낱말을 보지 않는다. 기존 글자를 재배열·반복해 새 내용을 만들어도 경고 없이 제안을 고를 수 있다. 계획의 “두 후보에 없는 낱말” 감지보다 범위가 좁다.
- **고칠 방향:** 두 후보에서 순서를 유지해 가져온 구간인지 검증한다. 확실히 입증하지 못하는 합친 제안은 원본 확인 경고를 표시한다. 보정 지침에도 인용 구간만 조합하도록 제약을 둔다.

### M10. Qwen 단독 페이지에서는 그림 설명을 끄는 UI에 도달할 수 없다

- **파일:줄:** `app/web/app.js:7765`, `app/web/app.js:7969`, `app/web/app.js:8142`, `app/ocr_compare.py:240`.
- **재현·근거:** Qwen만 읽은 묶음의 원본 보기에는 ‘닫기 / 이 쪽 글 고치기 / 페이지 빼기’만 나타났다(Node 재현). `r.cmp`가 없어 차이 검토 버튼이 없고, 그림 설명 체크박스는 차이 검토 창에만 있다.
- **영향:** 설명은 기본으로 본문에 들어가지만 결정 6의 페이지별 켜기·끄기가 불가능하다. CLOVA 실패로 비교할 수 없는 쪽도 마찬가지다. 전체 글을 직접 편집해서 지우는 것은 가능하지만, 도움말에 안내한 그림 설명 확인·끄기와 다르다.
- **고칠 방향:** 원본 보기에도 그림 설명·전환 체크박스를 두고, Qwen 결과가 있으면 엔진 비교 유무와 관계없이 제공한다.

### M11. Qwen은 응답을 못 받으면 사용자 확인 없이 같은 쪽을 재전송한다

- **파일:줄:** `app/ocr_vision.py:141`, `app/ocr_vision.py:145`, `app/ocr_vision.py:155`.
- **근거:** `read_page`는 연결 예외·서버 오류에서 최대 2번 POST한다. 가짜 503 응답으로 POST 2회를 확인했다. 요청이 제공업체까지 도착한 뒤 응답만 끊긴 경우도 동일하게 재전송할 수 있다.
- **영향:** 엄밀한 “쪽마다 한 번 전송”은 보장되지 않는다. 첫 시도의 처리 여부·비용은 저장되지 않고 마지막 성공 응답의 비용만 남는다. **실제 중복 과금은 확인하지 않았다.**
- **고칠 방향:** 전송 전 실패와 처리 여부를 모르는 실패를 구분한다. 후자는 자동으로 재전송하지 않고 저장된 상태와 비용 가능성을 알린 뒤 사용자가 재시도하게 한다. 자동 재시도를 유지하기로 한다면 예외 정책·횟수·추가 비용 가능성을 계획과 UI에 명시한다.

## 낮은 심각도

### L1. 같은 줄 뒤의 그림 설명 여러 개가 역순으로 들어간다

- **파일:줄:** `app/ocr_compare.py:154`, `app/ocr_compare.py:197`.
- **재현:** `figures=[{after_line:0, desc:"첫 그림"}, {after_line:0, desc:"둘째 그림"}]`. 하이브리드 최종 글에는 ‘둘째 그림’→‘첫 그림’ 순으로 들어간다. Qwen 단독 `page_text`와도 순서가 다르다.
- **고칠 방향:** 같은 위치의 삽입을 먼저 한 덩어리로 합치거나, 역방향 치환 시 동일 위치의 순서도 뒤집어 처리한다. 앞/중간/끝의 복수 설명과 삭제 경계가 겹치는 경우를 시험한다.

### L2. 좁은 창에서 검토 창 전체가 한 열로 바뀌지 않는다

- **파일:줄:** `app/web/app.js:7939`, `app/web/style.css:466`, `app/web/style.css:2138`, `app/web/style.css:2161`.
- **근거:** 바깥 원본/결과 그리드는 인라인 `minmax(260px,38%) 1fr`이다. 안쪽 후보·4개 버튼만 760px 이하에서 줄어들고, 바깥 그리드와 줄바꿈 없는 `.sheet-head`에는 대응 규칙이 없다. 작은 폭에서는 오른쪽 칸·머리글이 넘칠 여지가 크다.
- **고칠 방향:** 바깥 그리드도 클래스와 미디어 쿼리로 한 열로 바꾸고, 머리글 탐색 버튼을 줄바꿈한다. 실제 600px 안팎 창과 글자 크기 150%에서 확인한다. 실제 넘침 정도는 브라우저 금지 조건 때문에 시각 확인하지 못했다.

### L3. 보안·도움말 일부 문구가 새 동작과 어긋난다

- **파일:줄:** `app/web/index.html:827`, `app/web/index.html:829`, `app/web/index.html:638`, `app/web/index.html:883`, `app/web/app.js:8121`.
- **근거:** Qwen 머리글 가림을 설명한 바로 뒤에 ‘앱이 이미지 속 인적사항을 가려 주지는 않습니다’가 남아 있다. ‘학번·이름은 AI 미사용’과 ‘AI로 보내지 않음’도 Qwen이 먼저 읽는 경우·그림 자체를 전송한 경우를 구분하지 않는다. 보정 제안의 ‘이름·학번은 ○○’ 보장은 H3의 실제 동작보다 강하다.
- **고칠 방향:** ‘CLOVA에는 원본, Qwen에는 지정한 위쪽 영역만 가림, 읽힌 글에서 신원 추출은 로컬 규칙’으로 나누어 쓴다. 그림 읽기는 Qwen, 글자 판단은 AI 제안이라는 구분은 새 검토 화면에 대체로 잘 반영됐다. 실제 버튼명이 [AI 제안]인 곳과 설정의 [AI 보정 제안 받기] 안내도 맞춘다.

## 요청 항목별 추가 확인

| 항목 | 확인한 내용 / 남은 범위 |
|---|---|
| 엔진 간 저장 경쟁 | 한 번의 OCR 실행 안에서는 CLOVA 저장·Qwen 페이지별 저장이 동일한 `store_lock`을 사용한다. 이 경로 자체의 단순 덮어쓰기는 발견하지 못했다. 검토·제안까지 포함하면 M6이 남는다. |
| 옛 묶음 | 기존 시험의 `sc.ocr`만 있는 묶음 읽기, 직접 고치기·되돌리기는 통과했다. 옛 묶음에는 `sc.clova`가 없어 ‘Qwen으로도 읽어 비교하기’ 버튼이 나오지 않는다. 과거 텍스트를 좌표 없는 CLOVA 결과로 승격할지 별도 정책이 필요하다. |
| 다시 읽기와 review | `scan_reset_engine`은 `review={}`로 지운다. UI의 전체 재실행 확인도 ‘결과와 차이 검토를 모두 지운다’고 안내한다. 실패한 Qwen 쪽만 재시도할 때 정상 쪽의 결과와 가림 값은 유지되는 기존 시험이 통과했다. |
| 호출 경로 | 비교·고르기·다시 묶기·원본 보기·확대 자르기는 외부 API를 호출하지 않는다. 새 CLOVA 묶음에 Qwen 추가 시 CLOVA는 캐시를 사용한다. 중지/실패 이후 호출 보장은 M2·M3·M11의 예외가 있다. |
| 개인정보·제공업체 | 모든 Qwen `payload`에 `data_collection=deny`, `zdr=True`, `require_parameters=True`가 들어간다. 실제 제공업체 수락·보존 정책은 재검증하지 않았다. 가림 바이트 처리는 기존 시험의 흰색 영역 검사로 확인했다. 실제 유효 가림·동의는 H2가 남는다. |

| 빈 결과 | CLOVA/Qwen 중 한쪽 글만 빈 경우를 곧바로 ‘크게 다름’으로 표시하지 않고 차이로 만든다. 실패 객체는 M1과 별개로 처리해야 한다. `ocr_pdf_pages`는 응답에 없는 페이지를 정상 빈 페이지로 채우므로 실제 백지와 누락 응답을 구별할 수 없다. 누락 응답은 실패 상태로 분리하는 편이 좋다. |

| XSS·키 노출 | 추가 UI의 OCR 본문·후보·그림 설명·제안 이유·오류는 `text`/텍스트 노드로 넣고, 동적 모델명을 HTML에 넣는 곳은 `escHtml`을 사용한다. 추가분에서 직접적인 모델/OCR 글의 HTML 삽입 취약점은 발견하지 못했다. 연결 예외는 클래스명만 표시하고 키를 직접 넣는 로그는 발견하지 못했다. 서비스 오류 문구 일부는 그대로 보여 주므로 외부가 비밀을 되돌려 쓰는 경우까지 보장하는 것은 아니다. |
| 키보드 | 1·2와 ↑↓ 핸들러 및 입력 칸 예외는 있다. 선택할 때 DOM을 통째로 다시 그리므로 스크롤한 상태에서 포커스가 유지되는지는 실제 앱 시험이 필요하다. M8의 응답 순서 문제는 Node에서 재현했다. |

## 합치기 전 권장 확인

1. H1~H3을 먼저 수정하고, PDF 렌더링 직렬화·0% 차단·개인정보 분할 경계 시험을 추가한다.
2. 정상/빈 결과/페이지 실패/엔진 실패/중지를 조합해, 이미 받은 결과를 버리지 않고 외부 호출 없이 다음 단계로 갈 수 있는지 확인한다. 11쪽 이상 CLOVA 중간 실패와 Qwen 응답 불명확 실패를 포함한다.
3. 선택 두 개 동시 저장, 페이지 이동 응답 역전, 검토 창 왕복 후 학생 경계·제외 상태, 단위와 단어·줄 삽입을 회귀 시험으로 묶는다.
4. Qwen 단독에서도 그림 설명을 끌 수 있게 하고, 실제 Mac/Windows 앱에서 좁은 창·글자 150%·키보드 연속 선택을 확인한다.

이 검토에서는 실제 API 정확도·과금·제공업체 상태, 실제 Chrome/앱 렌더링, Windows 배포본, 네이티브 충돌 재현을 확인하지 않았다. 결과 문서 외 코드·시험·기존 문서를 수정하지 않았고 git fetch/pull/commit/push도 하지 않았다.
