- 검토일: 2026-11-09

- 대상: 컴퓨터에 익숙하지 않은 고등학교 교사, Windows exe·pywebview
- 요구사항: `docs/REQUIREMENTS.md:49–55`의 D2-7~D2-13
- 검토 방법: 변경 내역과 화면·연결·저장 코드 검토, 제공된 `v13_*.png` 확인, 임시 데이터 디렉터리를 이용한 로컬 Python 재현. Chrome이나 앱 GUI는 실행하지 않았다. Windows/WebView2 실기 조작·배율별 검증은 수행하지 않았다.

## 전체 판단

공통 일괄 버튼을 학생 칸 밖으로 옮긴 방향은 적절하다. 학생 한 명 추가와 반·과목 전체 입력의 구분이 이전보다 명확하고, 좁은 창에서 기록 다음에 최종안을 붙이는 배치도 자연스럽다. 최종안 덮어쓰기를 기본 해제하고 마감 학생을 제외한 점은 유지해야 한다.

다만 초보 교사가 안심하고 일괄 처리하기에는 **미리보기 수정 보존, 학생 식별 충돌 안내, 덮어쓰기 전문 비교, 입력 중 연속 클릭 방지**가 먼저 필요하다. ‘확정’이나 ‘보냄’이라는 표시를 그대로 믿으면 실제 처리와 기대가 어긋나는 경우가 있다. 아래 ‘높음’ 4건을 우선 처리하고, 이어서 처리 상태 표시와 칸 접기 구조를 정리하는 것을 권한다.

심각도 기준: **높음**은 자료 누락·중복 또는 잘못된 학생 연결·최종안 교체로 이어질 수 있는 문제, **중간**은 작업을 중단시키거나 선택 결과를 오해하게 하는 문제, **낮음**은 추적·표시 개선 사항이다. 각 항목에서 코드상 확정된 동작과 사용성 위험을 구분했다. 기존 공통 입력 화면에서 이어진 문제도 새 누가기록 일괄 입력에 동일하게 영향을 주면 포함했다.

## 상세 검토

### U01. 열 설정을 나중에 바꾸면 미리보기에서 한 수정이 조용히 사라짐

- **심각도:** 높음
- **위치:** `app/web/app.js:1995–2008`, `2037–2053`, `2072–2077` — 두 일괄 입력 창
- **문제:** 열 선택이나 ‘첫 줄은 머리글’을 변경하면 원본 `st.raw`로 다시 연결하고 `st.rows` 전체를 교체한다. 표에서 고친 내용·학생 연결·추천 확정·줄 삭제·순서 변경은 원본에 반영되지 않으므로 사라진다. 변경 사실을 알리거나 되돌리는 장치가 없다. 코드로 확인한 동작이다.
- **사용자가 겪는 상황:** 30명의 연결을 확인하고 몇 문장을 고친 뒤 마지막에 날짜 열을 선택한다. 앞서 수정한 문장이 원래대로 돌아가고, 뺀 행이 다시 들어온다. 자동 확정된 행은 그대로 입력할 수 있어 교사가 재검토 필요성을 놓치기 쉽다.
- **제안:** ‘① 자료 붙여넣기 → ② 열 지정 → ③ 학생·내용 확인 → ④ 추가’로 단계를 나눈다. ③에서 열을 다시 지정할 때는 수정 내역을 보존하거나, 초기화될 내역을 알리고 사용자가 선택하게 한다. 열 재계산 중에는 입력 버튼을 잠그고 마지막 설정에 대한 응답만 반영한다.

### U02. 학번과 이름이 서로 다른 학생을 가리켜도 ‘확정’ 표시

- **심각도:** 높음
- **위치:** `app/existing.py:129–145`, `app/web/app.js:2029`, `2045–2047` — 학생 연결 확인 표
- **문제:** 학번의 학생과 이름이 다를 때, 이름이 명렬에서 유일하면 이름 기준으로 경고 없이 확정한다. 반대로 학번·이름이 같으면 반·번호 충돌을 확인하지 않고 확정한다. 표의 원본 칸에는 `ext_no`가 표시되지 않아 충돌을 대조하기도 어렵다. D2-7의 ‘학번·반/번호는 확인용’이 충돌 상황에서 충분히 작동하지 않는다.
- **사용자가 겪는 상황:** 엑셀 정렬 실수로 이영희의 학번 `20102` 옆에 김철수라는 이름이 붙는다. 명렬에 김철수가 한 명이면 김철수에게 ‘확정’되고, 교사는 초록 표시를 보고 넘어간다.
- **확인:** 가상 명렬 `20101 김철수 / 20102 이영희`와 입력 `20102 / 김철수 / 내용`으로 `existing.build()`를 실행했다. 결과는 `student_no=20101`, `state=confirmed`, `note=''`였다.
- **제안:** 이름 중심 연결은 유지하되, 제공된 식별 정보가 충돌하면 ‘확인 필요’로 두고 `학번은 이영희, 이름은 김철수`를 표시한다. 원본 학번과 반·번호를 함께 보여주고 교사의 명시적 선택 후에만 확정한다.

### U03. 덮어쓰기 전 두 문장을 끝까지 읽기 어려움

- **심각도:** 높음
- **위치:** `app/web/app.js:2105`, `2141–2142`, `2163`; `app/web/style.css:526`; `app/records.py:267`, `551–558` — 최종안 일괄 확인 표
- **문제:** 보내려는 원문과 현재 최종안을 한 줄 말줄임으로 표시하며 전문은 마우스 `title`에만 제공한다. 클릭해서 전문을 펼치거나 차이를 비교하는 기능이 없다. 마지막 확인도 인원만 제시한다. 적용은 기존 최종안의 텍스트를 교체하며 이 경로에는 이전 최종안 복원 기능이 없다. 후보나 백업으로 복원 가능한 경우가 있더라도, 직접 수정한 최종안의 복구를 이 화면에서 보장하지 않는다.
- **사용자가 겪는 상황:** 첫 문장은 같고 뒤쪽 표현만 수정된 두 장문을 보고 오래된 문장으로 덮어쓴다. 도움말 풍선을 기다려 비교하는 방법을 모르거나 긴 글을 한 번에 대조하지 못해 수정분이 사라진다.
- **제안:** 각 행에 ‘전문 비교’를 두어 변경 전·후를 줄바꿈된 두 영역으로 펼친다. 덮어쓰기 확인에는 학생 이름과 인원을 함께 표시하고 실행 버튼을 `N명 최종안 덮어쓰기`로 구체화한다. 적용 전 최종안을 보관하고 완료 뒤 일괄 되돌리기를 제공한다. 단순한 경고창 추가보다 비교와 복구가 우선이다.

### U04. 입력 버튼 연속 클릭 시 같은 기록이 중복 추가될 수 있음

- **심각도:** 높음
- **위치:** `app/web/app.js:171–174`, `2079–2084`; `app/records.py:209–232` — 일괄 입력 실행
- **문제:** 적용 요청을 기다리는 동안 버튼 비활성화나 실행 중 가드가 없다. `mutate()`도 중복 실행을 막지 않으며, 저장은 매 요청마다 추가한다. UI의 빠른 두 번 클릭을 실기 재현한 것은 아니지만, 중복 요청이 모두 저장되는 것은 로컬 API 호출로 확인했다.
- **사용자가 겪는 상황:** Windows에서 반응이 늦어 보이자 교사가 입력 버튼을 한 번 더 누른다. 누가기록은 같은 내용이 다음 회차로 다시 붙고, 기존 완성문은 여러 개가 되어 이후 ‘최근 것’ 선택까지 영향을 준다.
- **확인:** 임시 학년도·학생에 같은 누가기록 payload를 두 번 적용했다. 두 요청 모두 성공했고 같은 내용이 회차 1·2로 저장됐다.
- **제안:** 클릭 즉시 `입력 중…`으로 바꾸고 적용·열 변경·재시작 버튼을 잠근다. 서버도 요청 식별자로 같은 실행의 재전송을 한 번만 적용한다. 의도적으로 같은 내용을 새 기록으로 추가하는 행위와 동일 요청 재전송은 구분해야 한다.

### U05. 체크를 해제해도 ‘보냄’ 상태가 유지됨

- **심각도:** 중간
- **위치:** `app/web/app.js:2125–2148` — 최종안 일괄 확인 표의 처리·요약
- **문제:** 처리 배지는 체크 여부가 아닌 학생의 분류로 정해진다. 빈 최종안 행의 체크를 해제해도 초록 ‘보냄’ 배지는 남고, 체크하지 않은 덮어쓰기 행에도 ‘덮어쓰기’가 표시된다. 요약의 ‘제외’는 시스템상 제외만 집계하므로 직접 해제한 행은 포함되지 않는다. 실행 대상은 체크 기준으로 올바르게 계산하지만 표시가 이를 충분히 설명하지 않는다.
- **사용자가 겪는 상황:** 한 학생을 빼려고 체크를 지웠는데 여전히 ‘보냄’이라고 나와 저장될지 불안해한다. 이미 처리가 끝난 상태라고 해석할 수도 있다.
- **제안:** 선택 결과는 `새로 반영 예정 / 덮어쓰기 예정 / 이번에는 제외`로 표시하고, 조건은 `최종안 없음 / 최종안 있음 / 마감`으로 분리한다. 요약을 `반영 N명(새로 A명·덮어쓰기 B명), 제외 C명`으로 만들어 전체 학생 수와 합계가 맞게 한다. 미실행 상태에는 과거형 ‘보냄’을 피한다.

### U06. ‘가장 최근 것’의 기준과 선택된 버전을 알 수 없음

- **심각도:** 중간
- **위치:** `app/records.py:238–240`, `282–307`; `app/web/app.js:2117–2118`, `2154`
- **문제:** 최근 것은 수정일이 아니라 마지막으로 생성된 ID 기준이다. 확인 표에는 제목·추가 시각·수정 시각이 없고 ‘N개 중 가장 최근 것’만 나온다. 나중에 다듬은 이전 기록이 선택될 것이라는 기대와 어긋난다. ‘최근’의 기준은 요구사항에도 정의가 없다.
- **사용자가 겪는 상황:** 먼저 넣은 글을 오늘 최종 수정하고, 나중에 넣었던 참고용 글은 그대로 둔다. ‘가장 최근 것 사용’을 보고 오늘 고친 글이 반영될 것이라 생각하지만 참고용 글이 선택된다.
- **제안:** 현 동작을 유지한다면 `마지막으로 추가한 완성문 사용`이라고 명시한다. 선택된 기록의 제목·추가일·수정일과 전문을 보여준다. 기본값을 바꾸기보다 ‘최근’의 정의를 요구사항에 확정하고 화면과 맞추는 것이 먼저다.

### U07. ‘제외하고 직접 고르기’가 선택 작업으로 이어지지 않음

- **심각도:** 중간
- **위치:** `app/web/app.js:2116`, `2151–2154`, `2170–2171` — 여러 완성문 옵션
- **문제:** 이 옵션은 여러 완성문이 있는 학생을 제외할 뿐, 이 창에서 원문을 고르거나 해당 학생 화면으로 이동하는 기능은 없다. 안내에는 학생 화면에서 고르라고 적혀 있지만 그 작업으로 이어지는 수단이 없다.
- **사용자가 겪는 상황:** 옵션을 누르면 선택 목록이 열릴 것으로 기대한다. 실제로는 행이 비활성화되어, 창을 취소하고 이름을 기억한 채 학생 목록에서 찾아야 한다.
- **제안:** 현재 기능이면 `여러 완성문이 있는 학생은 이번 일괄 처리에서 제외`로 정확히 표시한다. 별도로 `직접 선택이 필요한 학생 N명 보기`를 제공하거나 행에서 원문 선택을 지원한다. 학생 화면으로 이동할 때 나머지 일괄 선택은 보존한다.

### U08. 최종안을 접으면 후보 칸도 함께 사라짐

- **심각도:** 중간
- **위치:** `app/web/app.js:1857`, `1901–1903`; `app/web/style.css:513–519`; 제공 `v13_both_folded.png`, `v13_wide_folded.png`
- **문제:** 후보 영역이 `recFinal` 안에 있으므로 최종안을 접는 CSS가 후보 제목과 펼침 버튼까지 숨긴다. 최종안과 후보를 각각 접는 기능은 있지만, 최종안을 접은 채 후보만 볼 수 없다. 저장된 접기 상태가 다음 학생에게도 적용되어 후보를 찾기 더 어려워질 수 있다.

### U09. 공통 줄의 적용 범위가 현재 학생·검색 결과와 혼동될 여지

- **심각도:** 중간
- **위치:** `app/web/index.html:82–95`; `app/web/app.js:1448–1452`, `2097–2101` — 항목별 기록 상단
- **문제:** ‘이 항목 전체(반·과목)’라는 별도 줄은 좋은 개선이다. 다만 바로 위에 현재 학생 이름·이전/다음 버튼이 있고, 범위 설명은 작은 보조색 텍스트다. 학생 목록 검색·상태 필터와 무관하게 담당 전체를 조회하는 점은 버튼만으로 알기 어렵다. 기능 오류가 아닌 범위 인지 위험이다.
- **사용자가 겪는 상황:** 학생을 검색해 한 명만 보이게 하거나 ‘입력 중’ 학생만 표시한 뒤 일괄 최종안을 누른다. 화면에 보이는 학생만 처리할 것으로 기대했는데 다른 학생도 대상 표에 나타난다.
- **제안:** `2학년 3반 · 진로활동 전체 작업`처럼 실제 담당명을 줄 제목에 넣는다. 창에도 `학생 목록의 검색·상태 필터와 무관한 전체 명렬 대상`을 표시한다. 학생 칸에는 `김철수 학생 기록`처럼 대상 이름을 붙여 두 범위를 더 분명히 구분한다. 추가 확인창을 늘리기보다 범위를 계속 보이게 하는 방법이 적합하다.

### U10. ‘이미 쓴 생기부 → 기존 완성문 → 최종안’의 관계가 끊겨 보임

- **심각도:** 중간
- **위치:** `app/web/index.html:93–95`, `402`; `app/web/app.js:1603–1605`, `2083`, `2170`
- **문제:** 같은 자료가 입력 버튼에서는 ‘이미 쓴 생기부’, 다음 버튼에서는 ‘기존 완성문’이 된다. 일괄 입력 완료 메시지는 단순히 ‘입력했습니다’라서 최종안까지 반영됐는지 구분하기 어렵다. 도움말에는 관계가 있지만 작업 지점에 충분히 드러나지 않는다.
- **사용자가 겪는 상황:** 이미 완성한 문장들을 입력했으므로 내보내기에 나오리라 생각한다. 실제로는 기록으로 추가됐고 최종안 반영을 한 단계 더 해야 한다는 사실을 뒤늦게 안다.
- **제안:** 최초 입력 창에 `작성된 문장을 기록으로 추가합니다. 최종안 반영은 다음 단계입니다`라고 안내한다. 버튼·카드·후속 창에서 `이미 쓴 생기부(기존 완성문)`를 일관되게 연결하고, 완료 영역에 `N명에게 기록 추가 완료 → 최종안 반영 확인`을 제공한다. 추가는 기존 기록을 교체하지 않는다는 점도 명시한다. 최종안 반영과 마감은 별도 단계임을 함께 알린다.

### U11. 날짜 열을 직접 선택해도 읽지 못한 날짜가 경고 없이 빠짐

- **심각도:** 중간
- **위치:** `app/existing.py:157–168`, `197–199`; `app/web/app.js:2015–2024`, `2047` — 누가기록 일괄 입력
- **문제:** 날짜를 읽지 못하면 빈 문자열로 바꾸며 확인 필요 항목에 포함하지 않는다. 연도가 없는 `3/5`는 사라지고, 반대로 실제 존재하지 않는 `2026-02-31`은 통과한다. 미리보기는 정규화 결과만 보여주므로 원래 날짜와 비교하기 어렵다. 날짜 기본 ‘없음’은 요구대로이며, 여기서 문제는 **교사가 날짜 열을 명시적으로 선택한 뒤의 처리**다.
- **사용자가 겪는 상황:** 관찰일을 `3/5`로 적은 표에서 날짜 열을 골랐다. 모든 행이 확정이어서 입력했는데 날짜가 하나도 저장되지 않는다.
- **확인:** 날짜 열을 선택한 `existing.build()`에서 `3/5`가 `date=''`, `state=confirmed`로 반환됐다. `norm_date('2026-02-31')`은 그대로 `2026-02-31`을 반환했다.
- **제안:** 원본 날짜와 저장될 날짜를 함께 보여주고 `날짜를 읽지 못함 N건`을 집계한다. 해당 행에서 날짜 수정 또는 명시적 ‘날짜 없이 추가’를 선택하게 한다. 학년도 기준 연도 보완을 지원한다면 1·2월 처리 기준을 안내하고, 달력상 유효한 날짜를 검증한다.

### U12. 열 선택 목록에서 실제 머리글 대신 첫 학생 값만 보여줌

- **심각도:** 중간
- **위치:** `app/web/app.js:1991–2008` — 이름·내용·반/번호·학번·활동명·날짜 선택
- **문제:** 선택지는 `A열: 김철수`처럼 첫 데이터의 앞 10자만 표시한다. 머리글을 인식해도 `성명`, `활동일`, `관찰 메모` 같은 실제 열 이름은 표시하지 않는다. 원본 전체 표도 없어서 비슷한 내용 열이 여러 개면 판단이 어렵다.
- **사용자가 겪는 상황:** 엑셀에 ‘교사 메모’와 ‘학생 소감’ 열이 있고 둘 다 같은 말로 시작한다. 어느 열이 기록 내용으로 들어갈지 알기 위해 앞뒤 창을 오가야 한다.
- **제안:** `D열 · 관찰 메모 · “토론에서…”`처럼 열 문자·머리글·예시를 함께 표시한다. 머리글이 없으면 예시 2~3개를 제공한다. 필수 역할은 `이름 열`, `기록 내용 열`, 선택 항목은 `사용 안 함`으로 표기하고, 열 지정 단계에서 원본 일부를 확인하게 한다. ‘읽기’ 버튼도 `열·학생 연결 확인`으로 구체화한다.

### U13. 순서를 바꾸면 원본 행 번호를 추적할 수 없음

### U14. 클립보드 내용에 따라 시작 화면이 달라져 붙여넣기 흐름이 불안정함

- **심각도:** 중간
- **위치:** `app/web/app.js:1967–1970`, `1976–1985`, `2088` — 두 일괄 입력 창 진입
- **문제:** 클립보드에 탭이 있으면 즉시 읽어 연결 표로 진입하고, 없으면 빈 붙여넣기 화면으로 진입한다. 자동으로 읽었다는 출처 안내가 없다. 사용자가 이번 입력을 위해 복사하지 않은 오래된 표도 미리보기에 나타날 수 있다. 자동 저장되는 것은 아니지만 자료 선택 단계가 생략된다.
- **사용자가 겪는 상황:** 다른 업무 표를 복사해 둔 채 누가기록 입력을 누른다. 어디서 나온 자료인지 모르는 학생·문장이 나타나거나, 지난번과 화면이 달라 잘못 눌렀다고 생각한다.
- **제안:** 항상 같은 자료 선택 단계에서 시작하고 `클립보드 표 붙여넣기`를 명시적으로 누르게 한다. 자동 읽기를 유지한다면 `클립보드의 표 N행을 읽었습니다 · 아직 저장 전`과 ‘다른 자료 붙여넣기’를 눈에 띄게 제공한다. 이후 열 지정·연결 확인·추가 순서를 일관되게 보여준다.

### U15. 날짜를 넣지 않는 상태에도 오늘 날짜가 보임

- **심각도:** 낮음
- **위치:** `app/web/app.js:1711–1712`, `1722`, `1729` — 누가기록 추가·수정
- **문제:** 체크 해제 상태에서도 비활성 날짜 필드에 오늘 날짜를 표시한다. 저장에서는 날짜를 빼므로 요구 동작은 맞지만, 비활성 필드의 의미에 익숙하지 않으면 오늘 날짜가 저장된다고 생각할 수 있다. 기존 기록의 체크 해제는 기존 날짜 삭제를 의미한다는 설명도 없다.
- **사용자가 겪는 상황:** 날짜 없이 관찰 메모를 쓰려는데 화면에 오늘 날짜가 있어 이를 지우려고 한다. 수정 중에는 체크를 단지 날짜 입력칸 숨기기로 생각하고 해제해 기존 날짜를 없앨 수 있다.
- **제안:** 꺼진 상태는 `날짜 없이 저장`으로 표시하고 날짜 입력칸을 숨기거나 비워 둔다. 켜는 순간 오늘 날짜를 채운다. 날짜가 있던 기록을 수정할 때 해제하면 `저장하면 기존 날짜를 제거합니다`라는 짧은 설명을 보여준다. 일반 추가마다 확인창을 띄울 필요는 없다.

## 확인 결과와 남은 검증

`PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B tests/test_existing_import.py`는 `EXISTING IMPORT OK`로 통과했다. 테스트는 임시 데이터 디렉터리에서 실행하고 AI·잔액 함수는 로컬 대체 함수를 사용한다. 이름·NEIS 열 인식, 순서 저장, 여러 누가기록 회차 추가, 날짜 기본 제외·명시 선택, 최종안 반영과 마감 학생을 포함한 요청의 전체 취소가 확인됐다. 이 통과는 Windows에서의 클릭·배치 사용성까지 검증했다는 의미는 아니다.

별도 로컬 재현으로 U02의 식별 정보 충돌, U04의 동일 요청 중복 추가, U11의 날짜 누락·잘못된 날짜 허용을 확인했다. U01·U05·U08 등 화면 상태 문제는 코드 경로 및 제공 스크린샷을 근거로 판단했다. 기존 사용자 데이터는 사용하지 않았으며 코드·설정·assets를 수정하지 않았다.

제공된 1100×900 위아래 배치에서는 짧은 기록 아래 최종안이 이어지고, 1440×900 넓은 배치에서는 접힌 칸이 세로 막대가 되는 것을 확인했다. 다만 화면 높이를 고정하고 기록·최종안에 각각 스크롤을 주는 구조(`style.css:327–338`, `386–391`)이므로, 새 공통 줄이 여러 줄로 감기는 낮은 창은 Windows 실기 확인이 필요하다. 출시 전 1366×768 환경의 125%·150% 배율에서 다음 작업을 확인할 것을 권한다. 아래는 미재현 버그 목록이 아니라 남은 검증 항목이다.

- 긴 학생명·과목명, 기록 0건·1건·30건에서 학생 추가·종합·마감 버튼에 접근할 수 있는지
- 학생 목록 표시/숨김 및 세 영역 접기 조합에서 가로 잘림·스크롤 막힘이 없는지
- 일괄 입력 표의 열 지정과 하단 실행 버튼을 함께 찾을 수 있는지, 키보드로 전문 확인·확정·제외가 가능한지
- 변경한 연결·문장·제외 행이 열 재지정과 오류 후 재시도에도 보존되는지
- 실제 pywebview에서 느린 응답 중 연속 클릭이 한 번만 적용되는지
