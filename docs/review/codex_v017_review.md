# v0.17 변경 코드·UX 검토

- 검토일: 2026-11-10
- 범위: `feature/v0.16`의 미커밋 diff, `AGENTS.md`, `tests/test_basis_gen.py`, `scripts/demo_mac.py`, 로컬 `tests/fixtures/v9_sample.sqlite`.
- 방법: 코드·자료 형식·시험 파일 검토, 지정 스크린샷 9장 확인, 임시 데이터와 대체 AI/HTTP 응답을 이용한 로컬 시험. Chrome·브라우저·실제 AI·업데이트 다운로드는 실행하지 않았다. 실제 사용자 자료는 변경하지 않았다.
- 스크린샷에는 v0.16 및 삭제 전 ‘일괄 종합’ 메뉴가 있는 사진도 있어 화면 밀도 참고로 사용했다. 최종 기능 판단은 현재 diff 기준이다.
- 심각도: **상**=출시/보호 절차 차단, 자료 손실·중요 안내 누락 위험, **중**=오생성·반복 비용·상태 오인·작업 방해, **하**=보조 설명·탐색 개선. C는 코드, U는 UX이며 각각 심각도 순으로 배치했다.

## 결론

**메뉴가 많다는 반응에는 근거가 있다. 다만 메뉴 수만 줄이면 해결되는 구조는 아니다.** 현재 메뉴는 화면의 종류와 업무 단계가 섞여 있고, 항목별 기록 한 화면에도 전체 대상 작업·학생 작업·기록 작업·후보 작업·최종안 작업이 함께 보인다. 처음 보는 교사는 ‘내가 지금 무엇을 먼저 해야 하는가’와 ‘어떤 버튼이 누구에게 적용되는가’를 동시에 배워야 한다. 실제 사용 전 인상이라는 점을 감안해도 화면에서 확인되는 부담이다.

권장은 **기존 자료·기능은 유지하면서 주 메뉴를 ‘홈 / 기록 / 자료 가져오기 / 검토·내보내기’로 정리하고, ‘관리·설정 / 도움말’을 보조로 두는 안**이다. 기록 화면은 ‘학생별 / 태그별’ 탭으로 묶고, 성취기준·활동 개요와 태그 관리는 관련 작업에서 열 수 있게 한다. 상세 제안과 비교는 U01~U10에 적었다.

코드에서는 v9→v10의 추가형 마이그레이션과 사전 백업 기본 동작은 통과했다. 먼저 처리할 것은 **CI에서 빠지는 v9 시험 파일(C01), 불완전한 업데이트 경고 수집(C02), 활동 개요 저장 실패 후 초안 복구(C03)**다. 생성 상태·재실행 동선도 수정해야 새 창이 실사용에서 복잡함과 비용을 늘리지 않는다.

## 1. 코드 검토

### C01. [상] v9 시험 파일이 Git에서 무시되어 깨끗한 CI에서 시험이 실패함

- **근거:** `.gitignore:7`의 `*.sqlite`; `.github/workflows/build-windows.yml:44`; `tests/test_basis_gen.py`의 `test_migration()`.
- **확인:** 로컬 파일은 존재하고 새 테스트도 통과한다. 그러나 `git ls-files tests/fixtures`에는 `scan_sample.pdf`만 있으며 `git check-ignore -v tests/fixtures/v9_sample.sqlite`는 `*.sqlite` 규칙을 반환한다. 현재 일반적인 추가 과정으로는 fixture가 변경 목록에 들어가지 않는다. 깨끗한 checkout에서는 `shutil.copy(src,dst)`가 파일 없음으로 실패한다.
- **제안:** 더미 fixture를 명시적인 예외 또는 강제 추가로 추적하고 깨끗한 checkout에서도 시험한다. 이는 `AGENTS.md` 3번의 이전 형식 CI 검증을 실제로 성립시키는 필수 조건이다. 현재 보고서에서는 파일·ignore·Git 인덱스를 수정하지 않았다.

### C02. [상] 업데이트 경고 조회·파싱이 불완전하면 입력 확인을 거치지 않음

- **근거:** `app/updater.py:33–70`, `93–122`; `app/api.py:1553–1561`.
- **확인:** 경고 문자열이 있으면 UI와 서버가 모두 ‘확인했어요’를 검사하는 점은 좋다. 하지만 경고가 없는 것과 경고를 확인하지 못한 것을 같은 빈 문자열로 취급한다. 로컬 대체 HTTP 오류에서 `warnings_between()`은 최신 노트에 경고가 없으면 `''`를 반환했다. 건너뛴 버전에만 중요 안내가 있다면 서버의 입력 확인도 적용되지 않는다. 릴리스 목록도 첫 30개만 읽으며 이후 페이지를 확인하지 않는다. 또한 `## ⚠ 업데이트 전 꼭 읽기` 바로 아래 `### 메뉴 변경`을 넣으면 첫 하위 제목에서 수집을 끝내 `warning_of()`가 `''`가 됐다. 4000자 잘림은 긴 안내의 뒤쪽을 보이지 않게 할 수 있다.
- **제안:** `경고 없음 / 전체 범위 확인 완료 / 조회 불완전`을 구분한다. 확인 범위가 불완전하면 재시도·수동 전체 노트 확인 경로를 제공하고 자동 확인 생략으로 처리하지 않는다. 현재 버전까지 페이지를 따라가며 수집하고, 경고 절은 같은 수준/상위 제목에서만 끝낸다. 중요한 내용은 임의 잘림 없이 스크롤로 보여준다. 테스트에는 HTTP 실패·30개 초과·하위 제목·긴 노트를 추가한다.

### C03. [상] 활동 개요 저장 실패 뒤 다른 담당으로 이동하면 초안·재시도 경로를 잃음

- **근거:** `app/web/app.js:69–93`, `3855–3858`, `3992–3996`.
- **확인:** 활동 개요는 대기 저장에 넣지만 왼쪽 담당 버튼은 `leaveOk()` 없이 다른 편집기를 연다. 실패한 `runPending`은 대기 항목을 이미 삭제한 뒤 false만 반환하며, 옛 편집기는 사라져 복사·재시도가 없다. 실제 공통 함수 추출 실행에서 실패 후 `PENDING=0`, 다음 `flushPending()`은 true였다. 즉 새 활동 개요 경로에서도 실패한 초안이 지속되는 가드가 아니다. 같은 키의 이전 저장이 이미 실행 중이면 새 타이머가 그 요청 완료를 기다리는 구조도 아니므로 응답/쓰기 순서 검증이 필요하다.
- **제안:** 활동 개요별 초안·실패·진행 요청을 보존하고 동일 대상 저장을 직렬화한다. 담당/자료 종류 변경 전에 저장 성공을 확인하거나 초안을 유지한다. 실패 후 다시 읽어도 원문 초안을 복구할 수 있어야 한다. 파일·붙여넣기 교체도 저장 성공 전에 대기 초안을 버리지 않도록 한다. 기존 성취기준의 같은 저장 패턴까지 함께 확인하는 편이 좋다.

### C04. [중] 활동 개요 저장과 화면 전환이 끝나기 전에 생성 창을 읽을 수 있음

- **근거:** `app/web/app.js:4019`; `openRecords()`의 `showPanel('records')` 호출과 `showPanel()`의 비동기 저장 분기; `4048–4057`.
- **문제:** `await openRecords(...); openBasisGen(...)`는 ‘저장·화면 전환 완료’를 기다리는 계약이 아니다. `showPanel`은 저장을 `.then()`으로 시작하고 바로 반환한다. 따라서 방금 고친 활동 개요를 저장 중일 때 생성 창이 이전 DB 내용으로 열리거나, 저장 실패로 이동이 막혔는데도 생성 창을 열 수 있다.
- **제안:** 이동 함수를 성공 여부를 반환하는 await 가능한 흐름으로 만들고, 저장·전환 성공 뒤에 생성 창을 연다. 더 직접적으로는 활동 개요 저장 완료 후 해당 기준의 확정 스냅샷을 생성 창에 전달한다. 저장 지연·실패 상황을 시험한다. 이 항목은 코드 경로 확인이며 실제 GUI 클릭으로 재현하지 않았다.

### C05. [중] 최근 40개 일반 후보가 중복 회피용 기준 문장을 가림

- **근거:** `app/api.py:925–938`의 `_basis_avoid`.
- **확인:** 먼저 같은 담당의 다른 학생 synth 결과를 40개로 자른 후, 그 안에서 standards_only/outline_only를 찾는다. 임시 DB에서 기준 자료 후보 하나가 있을 때 회피 문장 수는 1이었으나 이후 일반 종합 결과 40개를 넣자 0이 됐다. 기준 자료 후보는 여전히 존재한다.
- **제안:** 기준 자료 기반 조건을 먼저 적용한 뒤 최근 문장을 고른다. 비교 기준이 ‘같은 담당’인지 ‘같은 자료 버전·선택 활동’인지도 명확히 한다. 다른 학생에게 이전에 생성한 문장을 피한다는 안내가 임의의 40개 컷 때문에 조용히 무효가 되지 않아야 한다.

### C06. [중] 생성 후 학생 상태가 과거 스냅샷이라 다시 ‘미입력’으로 고름

- **근거:** `app/web/app.js:4064–4070`, `4085–4091`, `4116–4119`, `4158–4175`; `app/records.py:793` 이후 `batch_info`.
- **확인:** `isEmpty`는 기록·최종안만 보며 후보는 세지 않는다. 생성 후에도 info.students를 갱신하지 않는다. 임시 API에서 후보를 만든 학생이 `records=0`, `has_final=False`, `all_locked=False`여서 이 조건상 계속 미입력이다. 스크린샷 b_result도 후보 생성 성공 옆 상태가 여전히 미입력이다. 일부 성공/실패/중지 때는 성공이 있으면 전체 선택을 비우고 미실행 표시는 별도로 남기지 않는다.
- **제안:** 공통 상태 기준처럼 후보가 있으면 입력 중으로 갱신하고, ‘한 번도 후보를 만들지 않은 학생’과 ‘최종안 없음’을 구분한다. 성공·실패·미실행을 각각 기록해 실패/미실행만 이어서 실행하게 한다. 재선택 한 번으로 성공 학생의 크레딧을 다시 쓰거나 오래된 후보를 밀어내지 않게 한다.

### C07. [중] 새 여러 명 생성은 전체 작업 예약을 하지 않음

- **근거:** `app/web/app.js:4143–4164`, `4265–4266`; `app/api.py:107–115`, `942–977`.
- **문제:** 인박스 여러 건 실행에 쓰는 `jobStart/jobEnd`와 달리 새 생성은 aiRun만 호출한다. 서버는 학생 한 건의 `_ai_keys`만 알고 있어 학생 사이·성취수준 저장 단계 등에서 전체 생성이 진행 중인지 알지 못한다. 진행 창의 inert는 UI 조작을 상당 부분 막지만 서버의 관리 작업 배타 예약을 대신하지는 않는다.
- **제안:** 승인 후 전체 생성 시작~종료를 서버 job 예약과 try/finally로 감싼다. 학년도 전환·백업 복원·업데이트·종료와 겹치는 시험을 추가하고, 실행 요청에는 기대 학년도도 고정한다. 현재 일반 UI에서 복원이 겹쳐 자료가 손상됐다고 재현한 것은 아니며 배타성 보장 누락으로 분류한다.

### C08. [중] 담당 삭제 영향 안내에서 새 활동 개요가 누락됨

- **근거:** `app/db.py:419–442`, `163–170`; `app/web/app.js:533–536` 부근 삭제 안내.
- **문제:** outlines는 그룹 삭제 시 외래키 cascade로 삭제되지만 group_impact와 확인 문구에는 활동 개요가 없다. 기록·최종안이 없는 담당에도 개요는 있을 수 있어 삭제 대상이 명확히 전달되지 않는다. 삭제 전 자동 백업은 복구 수단이며 영향 안내의 누락을 대신하지 않는다.
- **제안:** 영향 정보와 확인창에 활동 개요 건수/종류를 포함한다. 백업 복원 시험에도 outlines 내용과 연결을 포함한다. 일반 삭제 권한 자체를 문제 삼는 것이 아니라 새 자료를 삭제 안내에 포함해야 한다는 의미다.

## 2. UX 검토 — 처음 쓰는 교사에게 왜 복잡해 보이는가

### U01. [상] 업무 단계와 관리 도구가 같은 메뉴 층위에 있음

- **근거:** `app/web/index.html:35–47`. 현재도 현황판·인박스·항목별 기록·태그별 기록·내보내기·명렬·태그 관리·성취기준/개요·설정·안내·유의 사항 등 11개 선택지가 있다. 일상 업무, 최초 준비, 보조 조회, 설명 문서가 같은 수준이다. b_outline·tc_tagrec 사진에서도 사용하지 않는 메뉴가 항상 보인다.
- **제안:** 단순히 삭제하지 말고 작업 빈도와 맥락으로 재배치한다. 다음 세 안을 비교하면 **B를 권장**한다. 실제 초보 교사에게 ‘메모 한 건 입력→후보 생성→검토·내보내기’ 과제를 주어 첫 클릭·막힌 곳을 확인한 뒤 확정한다. 아직 써보지 않은 동료 한 명의 인상만으로 모든 기능을 숨기지는 않는다.

| 안 | 구성 | 장점 | 단점·조건 | 판단 |
|---|---|---|---|---|
| A. 현재 메뉴를 제목 아래 묶기 | ‘기록 작업 / 준비·관리 / 도움말’ 구역 | 경로 변화가 작고 구현·이전 사용자 적응 부담이 낮음 | 11개가 계속 보여 선택 부담 감소는 제한적 | 먼저 적용하기 좋은 최소 변경 |
| B. 주 메뉴 4개+보조 2개 | 홈 / 기록 / 자료 가져오기 / 검토·내보내기, 아래 관리·설정 / 도움말 | 작업 흐름을 읽기 쉽고 일상 선택 수가 줄어듦 | 탭·관련 바로가기와 기존 경로 호환이 필요 | **권장** |
| C. 모든 것을 기록 한 화면에 통합 | 가져오기·매칭·기준 자료·태그·기록·최종안을 한 화면 | 메뉴 수는 가장 적음 | 매칭 전 자료와 학생 기록의 상태가 다르고 버튼 밀도가 더 커짐 | 첫 화면 마법사로만 제한 권장 |

권장 B의 ‘기록’ 안에는 **학생별 / 태그별** 탭을 둔다. ‘관리·설정’은 명렬·담당, 기준 자료, 태그 관리, 연결·모델, 백업·자료를 담되 처음 설정에는 명렬/연결로 바로 안내한다. ‘자료 가져오기’는 현재 인박스의 단계와 임시 자료를 그대로 유지한다.

### U02. [상] 메뉴를 줄이는 동안 자료의 위치·범위를 함께 바꾸면 안 됨

- **근거:** `AGENTS.md` 1~5번. 현재 인박스에는 보내기 전 원본·매칭·후보가 있고, 학생 기록에는 기록·태그·후보·최종안·마감이 있다. 기준 자료도 standards와 outlines로 구분된다. 태그별 기록은 다른 저장소가 아니라 동일 기록의 조회 방식이다.
- **제안:** 메뉴 통합은 먼저 **동일 ID·동일 저장소의 새로운 진입 경로**로 구현한다. 아래 자료 대응표를 이행 기준으로 삼는다. 불필요한 복사·재생성·삭제는 하지 않는다. 실제 표/열 추가가 필요하면 버전을 올리고 형식변경전 백업, 이전 형식 fixture, 레코드 내용·연결 보존 시험을 동반한다. 새 자리가 없으면 AGENTS 규칙대로 읽기 전용 이전 버전 자료와 내보내기를 제공한다.

| 현재 자료·화면 | 권장 새 자리 | 보존해야 할 것 |
|---|---|---|
| 항목별 기록·태그별 기록 | 기록의 학생별/태그별 탭 | records·record_tags의 동일 ID, 순서·태그·원문, 학생·담당 연결 |
| 일괄 종합에서 만든 후보 | 기록의 해당 학생 후보 | results의 문장·잠금·비용·모델·근거, finals의 채택·마감 상태 |
| 자료 인박스 | 자료 가져오기 | batches·rows·cands, 원문·스캔·매칭·제외·보낸 이력 |
| 성취기준·활동 개요 | 관련 담당의 기준 자료, 관리에서 전체 보기 | standards·outlines와 담당·학년도·출처 |
| 명렬·담당·수업 | 관리·설정 및 첫 설정 안내 | students·memberships·수업·활성/비활성·학기 합산 연결 |
| 태그 관리·설정 | 관련 탭의 관리 링크와 관리·설정 | 태그 사전·연결, 프롬프트·예시·모델·학년도·백업 접근 |

메뉴가 사라지는 릴리스 노트에는 ‘없어진 메뉴 → 새 위치 → 기존 자료 유지’를 각각 적는다. 기존 딥링크/화면 키는 새 위치로 연결하고, 통합 전 자료로 생성된 후보를 새 자리에서 확인·채택·내보내는 시험도 추가한다.

### U03. [중] ‘일괄 종합 삭제’와 ‘기준 자료 생성으로 대체’는 같은 기능이 아님

- **근거:** 삭제된 batch 패널은 여러 학생의 기존 기록을 종합했다. 새 `openBasisGen`은 기록이 있는 학생을 골라도 기록을 쓰지 않는다(`4040–4042`, `4184–4186`). 기존 후보 자료는 results에 남지만 기존의 여러 학생 기록 기반 종합 작업은 화면에서 사라진다.
- **제안:** 기능 축소가 의도라면 업데이트 안내에 분명히 적고 새 기능을 이전 기능의 단순 이동처럼 설명하지 않는다. 빈번한 기존 기록 종합이 필요하면 독립 메뉴를 되살리기보다 기록 화면의 고급 작업에 `여러 학생의 기록으로 후보 만들기`를 둔다. 기본 화면은 한 학생 생성으로 단순하게 유지할 수 있다. 자료 보존과 작업 기능 보존은 구분해 판단한다.

### U04. [중] 항목별 기록 화면에 서로 다른 대상의 버튼이 동시에 많음

- **근거:** `index.html:82–103`, `app.js:1849–1880` 부근, ai_records·b_update 사진. 전체 담당 일괄 입력 3개+여러 명 생성, 학생 추가·기존 문장 입력·기준 생성, 기록 선택·종합·태그·이동, 기록별 정제·수정·이동·삭제, 최종안 다듬기·마감이 동시에 보인다. 보라색만 강조해도 선택해야 할 동작 수는 줄지 않는다.
- **제안:** 기본 작업은 `기록 추가 → 후보 만들기 → 검토·마감` 세 덩어리로 보여준다. ‘전체 담당 작업’은 `여러 명 작업` 메뉴로, 태그 지정·이동·비중·모델은 필요한 시점의 확장 영역으로 둔다. 일괄 입력은 ‘자료 가져오기’ 및 ‘여러 명 작업’에서 경로를 제공하되 기능은 유지한다. 삭제·이동은 기록의 더보기로 보내 실수도 줄인다. 숙련자는 확장 상태를 기억하게 한다.

### U05. [중] 활동 참여 기본 ‘모두 켜짐’과 큰 학생×활동 표가 검토 부담을 키움

- **근거:** `app.js:4067–4068`, `4100–4102`, `4120–4125`; b_sheet·l_sheet 사진. 학생 30명·활동 15개라면 참여 여부를 수백 칸에서 확인해야 한다. 개별 칩은 14자 뒤 생략되고 위쪽 일괄 토글은 숫자만 보여 활동 번호를 기억해야 한다. 기본값은 모든 학생이 모든 활동에 참여한 것으로 해석된다.
- **제안:** `① 대상 학생 → ② 공통 참여 활동과 예외 → ③ 후보 검토`로 나눈다. 먼저 공통 활동을 전체 이름으로 고르고, 학생별 다른 점만 펼친다. 모두 참여 기본값을 유지한다면 실행 전에 ‘고른 학생의 공통 참여 활동을 확인했습니다’처럼 사실 확인을 분명히 한다. 이 체크는 사실을 자동 검증하는 기능이 아니다. 반·수업/미입력·후보 있음 필터로 대상도 줄여준다. 전체 표는 숙련자용 보기로 남길 수 있다.

### U06. [중] 생성 성공 뒤 문장을 볼 수 없고 다시 생성이 더 눈에 띔

- **근거:** `app.js:4104–4112`, `4161–4175`; b_result 사진. 결과 칸은 후보 생성·비슷함·다시 생성만 보여주고 생성 문장은 없다. 완료 후에도 상태가 미입력이며 최종안 후보를 보려면 창을 닫고 학생을 찾아야 한다. 실패·중지 학생을 이어서 선택하는 수단도 약하다.
- **제안:** 결과의 첫 행동을 `후보 보기`로 바꾸고 문장과 근거 활동을 펼친다. 필요하면 다른 학생과 전문 비교한다. `다시 생성`은 보조 행동으로 두고 비용·후보 교체를 설명한다. 완료·실패·미실행을 분리하고 `실패/미실행만 이어서`를 제공한다. ‘비슷함’만 보고 무한 재생성을 반복하지 않도록 안내한다.

### U07. [중] 50%는 품질·독창성 보장처럼 들리지만 실제로는 문구 겹침 참고값임

- **근거:** `standards.py:166–185`, `api.py:980–1006`, `app.js:4110`, `4150`. AI 지시는 ‘50% 이상 다르게’, 검사는 공백을 뺀 글자 3개 묶음의 Dice 비율이다. 같은 뜻을 다른 말로 썼는지, 실제 학생 모습이 다른지 판단하지 않는다. 비교도 담당의 기준 자료 기반 최신 후보끼리다. 데모 사진의 100%는 가짜 AI 응답 특성도 있으므로 실제 모델 성능으로 해석해서는 안 된다.
- **제안:** 기본 문구는 `표현 겹침이 높음·내용 비교 권장`으로 쓰고 수치는 자세히 보기에 둔다. ‘50% 다르게 보장’처럼 안내하지 않는다. 다른 활동/수준에 따른 실제 차이와 교사의 근거 확인을 우선한다. 이름·학번을 따로 보내지 않는다는 안내와 다른 학생 후보 문장이 추가 전송된다는 설명도 함께 유지한다.

### U08. [중] 상태색이 새 생성 창에서는 일관되게 적용되지 않음

- **근거:** `app.js:4090–4114`, `style.css:754–760`, b_sheet·b_result·b_sub 사진. 생성 표의 상태는 공통 STATUS 배지가 아니라 일반 글자·회색 st-empty·muted다. 마감은 회색으로 흐려지고 후보 생성 성공은 초록이다. 체크 행에는 기존 `.tbl tr:has(...checked)`의 초록 바탕·선이 적용되어 선택만 했어도 완료처럼 보인다. 후보가 생겨도 미입력으로 남는 C06이 이를 더 혼란스럽게 만든다.
- **제안:** 담당 상태는 **○ 회색 기록 없음 / ◐ 노랑 입력 중·후보 있음 / ◑ 초록 최종안 있음 / ● 파랑 마감**의 공통 배지를 쓴다. 후보 생성은 ‘이번 실행 성공’이지 생기부 완료가 아니므로 별도 열로 구분한다. 선택은 중립색+체크로 통일한다. 기록이 있는데 기준만 사용한 결과에는 ‘기록 없음’ 대신 `관찰기록 미사용·기준 자료로 생성`이라고 표시해 사실과 처리 방식을 구분한다.

### U09. [중] 보라색 AI와 다색 태그 글로우가 화면의 강조 우선순위를 흐림

- **근거:** `style.css:724–751`, `app.js:58–61`; ai_records·tc_tv2·tc_tagrec 사진. 보라색 AI 버튼은 행동 종류 구분에 도움이 된다. 하지만 모든 AI 버튼이 강하게 빛나고, 태그도 보라·남색·청록·라임 등으로 빛나 상태색의 초록·파랑·노랑과 가까워진다. 여러 개의 광택 강조가 같은 화면에서 경쟁한다. ‘상태색과 겹치지 않음’이라는 주석만으로 지각상 구분이 보장되지 않는다.
- **제안:** AI는 보라색을 유지하되 현재 단계의 주 버튼 하나만 강하게, 다른 AI는 테두리/작은 아이콘으로 둔다. 태그는 낮은 채도 바탕과 작은 색점·이름으로 식별하고 글로우는 줄인다. 태그색은 분류, 상태색은 진행 상태, 중립선은 선택이라는 역할을 범례 없이도 위치와 모양으로 구분되게 한다. 빨강 오류와 노랑 재검토는 장식색보다 우선해야 한다.

### U10. [중] 첫 화면에서 ‘자료 준비부터 모두 해야 한다’고 느끼기 쉬움

- **근거:** 메뉴의 명렬·성취기준/개요·태그·설정이 늘 보이고, 기록 화면에는 모델·목표·후보 보관 수·비중 등의 개념이 나온다. b_outline의 ‘모두 미리 넣을 필요 없음’ 안내는 있지만 사용자가 그 화면에 들어온 뒤 읽어야 한다. 기준 자료 고치기로 갔다가 생성 창을 다시 열면 학생별 참여/수준 선택을 새로 해야 한다(`4180–4181`).
- **제안:** 최초에는 `① 연결·명렬 준비 ② 학생 기록 한 건 넣기 ③ 후보 확인`을 홈에 제시한다. 자료 경로는 `직접 메모 / 엑셀·PDF 가져오기 / 이미 쓴 문장` 중 자신의 상황으로 고르게 한다. 기준 자료만으로 생성은 필요할 때 보이는 대안으로 둔다. 모델은 기본값을 보여주고 변경은 고급으로, 프롬프트·비중은 기본 접힘으로 둔다. 기준 자료 편집 왕복 때는 학생 선택·활동 예외를 보존하고 바뀐 기준만 재확인시킨다. 도움말과 유의 사항은 한 도움말 영역에 합치되 관련 작업에서 짧은 설명으로 연결한다.

## 상태색 화면별 정리

| 화면·표시 | 현재 판단 | 유지/개선 |
|---|---|---|
| 현황판·항목별 학생 목록 | 공통 네 상태 색과 기호·글자 사용 | 유지. ‘최종안 있음’과 마감은 별도 상태 |
| 태그별 기록 담당 머리 | 공통 상태 배지, 태그 선택 중립색 | 기본 방향 유지. 미입력 학생 현황은 이 화면의 역할이 아님 |
| 기록 체크 선택 | 초록 바탕·초록 선 | 완료 초록과 충돌, 중립 선택 표시로 통일 |
| 성취기준·활동 개요 목록 | 자료 있음 초록, 없음 기본색 | 준비 자료 있음 표시이며 학생 생기부 완료가 아님을 문구로 유지 |
| 기준 생성 학생 표 | 회색 미입력·회색 마감·일반 글자 상태 | 네 상태 공통 배지와 후보 상태 갱신 필요 |
| 생성 결과 성공 | 초록 ‘후보 생성’ | 실행 성공과 학생 완료를 분리 |
| AI 버튼 | 보라색·노랑 반짝임 | 기능 구분에는 도움. 주 행동만 강하게 강조 |
| 태그 | 8색 고정, 글로우·테두리 | 분류색이 상태색을 덮지 않게 채도·광택 축소 |

색만으로 모든 상태를 판정하게 하기보다 **상태는 고정 위치의 색+기호+글자**, 선택·자료 분류·실행 성공은 다른 위치와 모양으로 보여주는 편이 안전하다. Windows 실기 대비·흑백 식별은 이번 검토에서 측정하지 않았다.

## 자료 보존·백업 확인 결과

- v10은 outlines 표를 추가하며 기존 표·열 삭제/이름 변경은 diff에서 확인되지 않았다. 로컬 v9 fixture의 기존 TABLES 건수 유지·새 outlines 생성·변경 전 사본의 schema 9 유지 시험이 통과했다. 전체 내용·모든 연결까지 동일함을 증명하는 시험은 아니며 TABLES에는 inbox_cands 등이 빠져 있어 향후 보존 시험을 확대하는 것이 좋다.
- 열린 DB는 SQLite backup API를, 미개방 DB도 읽기 연결의 backup API를 사용한다. 형식변경전 백업 실패 시 해당 DB를 열지 않는 처리는 적절하다. 임시 백업 완료 뒤 게시하고 완료 마커를 쓰는 구조도 유지한다.
- 일반 백업은 최근 7개, **업데이트전+형식변경전은 합쳐 최근 3개**다. 종류마다 각각 3개가 아니다. 현재 테스트는 이 합산 규칙을 검증하며 AGENTS의 ‘하루 백업과 별도 최근 3개’와는 맞는다. ‘각각 3개’가 목표라면 규칙·구현·시험을 함께 바꿔야 한다. 일반 묶음에는 수동·복원전 등도 들어가므로 ‘하루 백업만 정확히 7일’로 설명하지 않는 편이 정확하다.
- `_premig_done`은 실행 중 한 번의 전체 사전 백업을 뜻한다. 복원으로 이전 형식을 다시 여는 경우, 사본 재유입, 여러 학년도, 백업 실패 재시도도 회귀 시험으로 남기는 편이 좋다. 이번 시험에서 이 경로의 자료 손상을 재현한 것은 아니다.
- 일괄 종합 전용 저장 표를 없앤 것은 아니며 기존 results·finals를 기록 화면에서 계속 조회한다. 메뉴 삭제만으로 기존 후보가 지워지는 코드도 diff에서 확인되지 않았다. 다만 U03의 작업 기능 축소와 C01의 CI fixture는 별도 문제다.
- `AGENTS.md`의 데모 사용자 확인은 push·태그 전에 요구된다. 이번 작업은 검토·보고서 작성이므로 데모 창을 실행하거나 릴리스 확인을 요청하지 않았다. `demo_mac.py`는 임시 자료 폴더·가짜 AI를 사용하고 자율·진로 활동 개요와 기존 기록/마감 예시를 추가했다. 실제 Windows 업데이트·배율 검증을 대신하지 않는다.

실제 OpenRouter·GitHub 요청과 업데이트 교체는 하지 않았다. 스크린샷의 100% 유사도는 데모 결과이며 실제 AI 품질 평가가 아니다. 실제 교사 사용성은 처음 과제를 수행하는 2~3명의 관찰로 확인하는 것이 다음 단계다. 화면 수나 클릭 수뿐 아니라 잘못 고른 대상·되돌아간 횟수·후보와 최종안을 혼동한 지점을 기록하면 메뉴 통합 판단에 도움이 된다.

이 보고서만 추가했다. 코드·AGENTS.md·fixture·스크립트·기존 문서는 수정하지 않았고 Chrome 실행·외부 전송·git commit/push도 하지 않았다.
