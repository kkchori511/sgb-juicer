검토일: 2026-11-22. 대상은 로컬 `feature/ocr-hybrid`의 **`20452df`**, 이전 상태 `f0b5e0d`와의 차이 및 `feature/v0.19`부터의 전체 추가분이다. 수정 커밋의 메시지와 달리 **17개 모두 완료로 판단하지 않는다. 10개는 고침, 7개는 일부, 안 고침은 0개**다. 원래 재현이 막힌 경우에도 관련 경계나 새 회귀가 남으면 ‘일부’로 적었다.

## 2. 남은 문제·회귀

### R1 — 높음 / H1 잔여: 비트맵 해제는 여전히 PDFium 잠금 밖

- **파일:줄:** `app/ocr_vision.py:68`, `app/ocr_vision.py:71`, `app/scan.py:192`, `app/scan.py:195`, `app/scan.py:218`, `app/scan.py:221`.
- **재현:** 설치된 `pypdfium2.raw.FPDFBitmap_Destroy`에 메모리 관측 래퍼를 씌워 실제 함수를 호출하고, 해제 순간 `scan.PDFIUM_LOCK._is_owned()`를 기록했다. `render_png`, `render_page`, `render_crop` 세 경로 모두 **False**였다. 실제 네이티브 해제를 생략하지 않았고 병렬 충돌을 일부러 유발하지도 않았다.
- **원인:** `pdf.close()`가 페이지는 정리하지만 렌더링 비트맵은 별도 자원이다. `bm`이 함수 끝까지 살아 있다가 `with PDFIUM_LOCK` 밖에서 소멸하며 네이티브 해제를 호출한다. 로컬 `pypdfium2/_helpers/bitmap.py:78`도 해당 해제 함수를 별도로 등록한다.
- **영향:** 한 스레드가 비트맵을 해제하는 동안 다른 스레드는 잠금을 얻어 문서 열기·렌더링을 할 수 있다. 기존의 ‘PDFium 모든 호출 직렬화’ 요건이 아직 성립하지 않는다. 6스레드 PNG 시험 통과가 스레드 안전성을 보장하지 않는다. 실제 프로세스 충돌은 재현하지 않았다.
- **고칠 방향:** 픽셀을 독립적인 `bytes`로 복사한 뒤, 비트맵도 같은 잠금 안의 `finally`/명시적 자원 문맥에서 닫는다. 예외 경로를 포함해 문서·페이지·비트맵의 모든 네이티브 정리를 보호한다. 해제 함수도 잠금 보유를 검사하는 시험을 추가한다.

### R2 — 높음 / H3 잔여: ‘1학년 3반 99번’에서 반·번호가 전송 글에 남는다

- **파일:줄:** `app/ocr_compare.py:304`, `app/ocr_compare.py:307`, `app/inbox.py:783`, `app/scan.py:15`.
- **재현:** 명렬에 `10399 / 가나다`가 있는 묶음에서 CLOVA 원문 `1학년 3반 99번 이름: 가나다`, Qwen 원문 `1학년 3반 98번 이름: 가나다`를 비교하고 실제 `scan_scrubber`→`fix_user`를 실행했다. 결과 일부는 다음과 같다.

```text
앞: 구 ○학년 3반 9 | CLOVA: 9 | Qwen: 8 | 뒤: 번 이름: ○○○
```

- **원인:** `redact`는 캡처 그룹이 있으면 무조건 **그룹 1만** 가린다. 이름·학번 정규식은 값이 그룹 1이지만, `RE_GCN`은 학년·반·번호가 각각 그룹 1·2·3이다. 추출한 정규 학번 `10399`는 `1학년 3반 99번`에 연속해서 나오지 않아 값 목록으로도 지워지지 않는다.
- **영향:** 일반적인 머리글 형식인데도 학생을 식별하는 반·번호가 후보와 문맥에 그대로 남는다. 본문에 쓴 임의의 타인 이름 탐지 한계와는 다른, 앱이 처리한다고 약속한 구조화된 신원 가리기의 누락이다.
- **고칠 방향:** 정규식별 지울 그룹을 명시해 `RE_GCN`은 세 숫자 그룹 모두 가린다. 값 사이에 띄어쓰기가 있는 경우와 각 숫자의 차이 경계도 시험한다. 이름·학번 라벨은 그대로 남겨도 값은 모두 가려야 한다.

### R3 — 중간 / M5 수정 회귀: 줄 끝 치환과 그림 삽입이 겹치면 다음 본문이 그림 줄에 붙는다

- **파일:줄:** `app/ocr_compare.py:139`, `app/ocr_compare.py:181`, `app/ocr_compare.py:216`, `app/ocr_compare.py:222`.
- **재현:** CLOVA `가나다\n라 마바`, Qwen `가나타\n라 마바`, 그림 `{after_line:0, desc:"장치 그림"}`. Qwen 차이를 고르고 그림 설명을 켜면 다음 결과가 나온다.

```text
가나타

[그림: 장치 그림]라 마바
```

- **기대:** `가나타\n[그림: 장치 그림]\n라 마바`처럼 그림과 다음 본문의 줄 경계를 지켜야 한다.
- **원인:** `a_ws`가 첫 줄 끝 개행까지 포함한다. `_fig_reps`는 원래 줄 끝의 그림 위치가 이 구간 안에 있으면 구간 끝, 즉 **다음 줄 시작**으로 옮긴다. 그 위치에 앞쪽 개행만 있는 그림 표시를 넣어 빈 줄이 늘고 뒤 본문과 붙는다.
- **고칠 방향:** 글 치환·공백 보존과 그림 삽입을 같은 경계 모델로 계산한다. 다음 줄 시작에 삽입할 때는 뒤쪽 개행을 보장하고, 적용하는 치환만 기준으로 위치를 조정한다. 그림 있음/없음·선택함/안 함·줄 끝 삭제/교체를 조합해 시험한다.

### R4 — 중간 / M6 수정 회귀: 저장 큐가 남아 있어도 닫고 매칭을 확정할 수 있다

- **파일:줄:** `app/web/app.js:7927`, `app/web/app.js:7938`, `app/inbox.py:824`, `app/inbox.py:699`.
- **화면 재현:** 실제 `showDiffReview`를 Node VM에서 실행해 선택 두 개를 누른 뒤 첫 저장 응답을 지연했다. 서버로 간 요청은 1개뿐이고 두 번째는 큐 안에 있었다. 이때 [닫기]가 곧바로 `loadBatch`를 실행했다. 첫 응답을 돌려준 뒤 **창이 닫힌 다음에 두 번째 저장이 전송**됐다.
- **자료 영향 확인:** fixture 묶음에서 첫 선택 후 `scan_confirm`으로 매칭 행을 만들고, 큐의 나중 선택에 해당하는 `inbox_scan_decide`를 보냈다. 나중 저장은 `ok=True`였지만 `scan.ocr`는 ‘넣어 준 **얼**은’, 이미 만든 Inbox 행은 ‘넣어 준 **열**은’으로 서로 달랐다. 실제 호출·학생 자료 없이 재현했다.
- **영향:** 사용자가 고른 뒤 바로 닫고 확정하면, 아직 저장되지 않은 선택이 최종 매칭 내용에서 빠질 수 있다. 백엔드 잠금은 개별 저장을 보호하지만 아직 서버로 보내지도 않은 큐 작업까지 기다려 주지는 않는다.
- **고칠 방향:** 닫기·다른 창 이동 전에 큐 완료와 오류 확인을 기다리고 최신 결과를 읽는다. 큐가 남아 있는 동안 다음 단계 확정을 막는다. 백엔드도 스캔 검토 버전과 매칭 생성 버전을 검사해 뒤늦은 저장이 다른 내용과 조용히 공존하지 않게 한다.

### R5 — 중간 / M8 잔여: 응답 대기 중 탐색 연타로 범위 밖 페이지를 요청한다

- **파일:줄:** `app/web/app.js:7950`, `app/web/app.js:7958`, `app/web/app.js:7959`, `app/inbox.py:683`.
- **재현:** 2쪽 묶음의 첫 쪽을 그린 뒤, 응답을 기다리는 동안 [다음 쪽]을 두 번 누른다. 실제 함수의 호출 기록은 `page=1`, 이어서 **`page=2`**였다. 유효 인덱스는 0·1뿐이다. 이 동안 첫 쪽의 이전 버튼은 여전히 비활성이다.
- **원인·영향:** `cur`는 즉시 증가하지만 버튼 활성 상태는 응답이 와야 다시 그린다. `nav` 자체에 경계 검사나 로딩 중 제한이 없다. 마지막 범위 밖 요청은 백엔드 인덱스 오류가 될 수 있고, 앞선 정상 응답은 `gen` 검사로 버려져 이전 화면에 남는다. 기존의 ‘다른 쪽에 선택 저장’은 고쳐졌으나 탐색 상태는 아직 어긋날 수 있다.
- **고칠 방향:** `nav`에서 `0 <= to < total`을 확인하고 대기 중 탐색 버튼을 갱신/비활성화한다. 백엔드도 페이지 범위를 검증해 명시적인 오류를 반환한다. 빠른 다음/이전 연타를 모두 시험한다.

### R6 — 낮음 / M9 수정 회귀: 기존 후보 그대로도 61자면 ‘새로 만든 글자’ 경고

- **재현:** 차이의 CLOVA 후보가 `가` 61자이고 AI 응답이 `pick="clova"`일 때 `parse_fix(...)["d0"]["new"]`가 **True**다. 새 글자는 전혀 없다.
- **원인·영향:** 60자 제한을 합친 글 검사뿐 아니라 기존 후보를 고른 경우에도 적용한다. 긴 차이에서는 정상 선택에도 ‘두 후보에 없는 글자를 만들었습니다’ 경고가 나와 경고 신뢰도를 떨어뜨린다.
- **고칠 방향:** 기존 후보와 정확히 같으면 `new=False`로 처리한다. 합친 글이 길어 검사를 생략한 경우는 ‘새 글자 확정’ 대신 ‘자동 검증하지 못함’으로 구분한다.

### R7 — 낮음 / L3 잔여: 저장되는 전송 동의의 범위가 설명과 다르다

- **파일:줄:** `app/web/index.html:346`, `app/web/index.html:826`, `app/web/index.html:862`, `app/api.py:2985`.
- **근거:** 설정 체크박스는 ‘Qwen만으로 읽을 때 … 동의’라고 쓰지만 같은 `ocr_ai_consent`가 하이브리드 0% 전송에도 적용된다. 보안 안내도 ‘Qwen만’의 무가림 동의만 설명한다. 새 사용자 결정에 따른 실제 범위를 설명하지 못한다.
- **고칠 방향:** ‘하이브리드·Qwen만에서 머리글 가림 0%로 전송’이라는 공통 범위를 쓰고, 동의가 설정에 저장되어 두 방식에 적용된다는 점을 맞춘다. 자동 재시도의 허용 예외(연결 전 실패·429·5xx)도 ‘한 번만’ 안내 옆에 짧게 적는다.

### R8 — 중간 / 앞 검토 미발견: Qwen 단독 완료 뒤 CLOVA만 추가하는 화면 경로가 없다

- **파일:줄:** `app/web/app.js:7906`, `app/web/app.js:7915`, `app/inbox.py:644`.
- **재현·근거:** 정상 Qwen 단독 결과를 가진 `sc`로 실제 `scanStatusBar`를 실행하면 동작 버튼은 **[OCR 다시 하기] 하나**다. ‘CLOVA만 추가해 비교하기’는 없다. 반대 방향인 CLOVA 완료→Qwen 추가만 구현되어 있다. 완료 뒤에는 읽는 방식 선택 화면도 나오지 않는다.
- **영향:** Qwen만 먼저 쓴 사용자가 나중에 CLOVA 키를 넣고 비교하려면, 노출된 경로에서는 [OCR 다시 하기]로 결과를 모두 지우게 된다. 하이브리드를 다시 실행하면 정상 Qwen까지 재전송된다. 계획 결정 4의 ‘한쪽만 읽은 묶음은 빠진 엔진만 추가’가 이 방향에서는 UI로 제공되지 않는다.
- **고칠 방향:** Qwen 원 결과와 처음 가림 값을 보존한 채 CLOVA의 미완료 쪽만 추가하는 버튼을 제공한다. 백엔드의 기존 캐시 재사용 경로를 연결하고, 이미 성공한 Qwen 호출 수가 늘지 않는지 확인한다.
