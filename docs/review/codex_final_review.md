## 요약 — 1.0 전 수정 권고

**현재 상태로 1.0 배포는 보류하는 것이 좋다.** 기본 작업 흐름과 기능은 상당 부분 구현되어 있고 기존 테스트 6개도 모두 통과했다. 그러나 추가 검증에서 개인정보 전송과 학생·학년도 간 자료 혼입, 백업·복원·되돌리기의 자료 손실이 재현됐다. 특히 SQLite 트랜잭션이 있다는 사실만으로 사전 검사와 여러 파일에 걸친 작업까지 보호되지는 않는다.

### 검토 방식과 증거 수준

- 요청서, 최신 `docs/REQUIREMENTS.md` A~J, `docs/design/LAYOUT.md`, 이전 UX 검토, Python/JS/HTML/CSS, 테스트와 Windows 빌드 워크플로를 읽었다.
- **재현 확인**: 임시 데이터 폴더에서 실제 백엔드 함수 또는 실제 JS 함수의 코드를 사용해 확인한 동작이다. AI·OCR 응답은 모의값이며 실제 자료는 전송하지 않았다.
- **코드 확인**: 소스에서 실행 경로를 확인했다. 실제 Windows 화면 조작 결과와 구분한다.
- 기존 테스트는 각각 독립 프로세스로 실행했고 모두 성공했다. `requests` 네트워크 호출과 브라우저 열기를 차단하고 OS 클립보드 쓰기를 모의 처리했다. `PYTHONDONTWRITEBYTECODE=1`로 실행하여 프로젝트의 바이트코드 파일도 쓰지 않았다.
- 코드는 수정하지 않았다. 이 결과 문서만 작성했다. Chrome 실행, 외부 게시·메시지 전송, git push는 하지 않았다.

### H02. 학년도별 인박스가 같은 PDF 파일을 공유함

- **우선순위 / 분류:** 높음 / 자료·버그

- **문제:** DB의 묶음 ID는 학년도마다 1부터 시작하지만 원본은 공통 `스캔/batch_1.pdf`에 저장된다. 다른 학년도의 같은 ID가 원본을 덮어쓰거나 삭제한다. 이전 학년도에서 다른 학생의 원본이 보일 수 있다.
- **재현·근거 — 재현 확인:** 2026년과 2027년에 첫 스캔 묶음을 만들자 모두 ID가 1이었다. 2027년 묶음을 삭제하니 2026년 묶음이 참조하는 PDF도 없어졌다. 파일 덮어쓰기는 `shutil.copyfile()` 경로에서도 확인된다.
- **고치는 방안:** `스캔/<학년도>/batch_<id>.pdf` 또는 학년도와 무관하게 유일한 원본 ID를 사용한다. PDF 읽기·OCR·원본 보기·삭제 모두 같은 명시적 학년도 식별자를 받게 한다. 기존 파일은 단순 복제만으로 소유 학년도를 판별할 수 없으므로 마이그레이션 시 충돌 여부를 알리고 복구 가능한 원본을 확인한다.
- **요구사항:** C3, J17.

### H03. 백업·복원에 스캔 PDF 원본이 포함되지 않음

- **우선순위 / 분류:** 높음 / 자료·요구사항
- **위치:** `app/backup.py:16`, `app/backup.py:23`, `app/backup.py:57`, `app/inbox.py:240`, `app/api.py:1109`
- **문제:** 백업은 SQLite만 저장한다. OCR 글자는 DB에 들어가지만 PDF는 별도 폴더에 있으므로 묶음 삭제나 파일 손상 후 DB를 복원해도 원본을 되찾을 수 없다. 학년도 삭제는 반대로 PDF를 지우지 않아 개인정보 원본이 남는 문제도 있다.
- **재현·근거 — 재현 확인:** 스캔 묶음 저장 → 백업 → 묶음 삭제 → 복원을 실행했다. 묶음 DB 행은 돌아왔지만 PDF는 없었다. `delete_year()`는 SQLite와 WAL/SHM만 삭제한다.
- **고치는 방안:** 학년도 DB와 해당 원본 파일을 하나의 백업 묶음으로 관리하고 목록·버전·완료 여부를 기록한다. 복원은 DB가 참조하는 동일 시점 원본을 함께 복원한다. 학년도 삭제 시 활성 원본 삭제 범위와 보존 백업 범위를 분리해 안내한다. 개인 설정·키를 백업할지는 별도 정책으로 명시하되, 평문 저장이라는 기존 사용자 결정을 바꿀 필요는 없다.
- **요구사항:** J17, J20–J21.

### H07. 동시에 두 번 보내면 한 묶음의 기록이 중복 생성됨

- **우선순위 / 분류:** 높음 / 자료·버그
- **위치:** `app/inbox.py:543`, `app/inbox.py:567`, `app/web/app.js:2077`
- **문제:** `stage == sent`와 명렬·마감 검사가 트랜잭션 밖에 있다. 두 요청이 사전 검사를 함께 통과하면 SQLite 쓰기가 순서대로 처리되더라도 두 요청 모두 기록을 추가한다. 보내기 버튼도 요청 중 비활성화하지 않는다.
- **재현·근거 — 재현 확인:** 실제 `send()`의 트랜잭션 진입 직전에 두 스레드를 맞춰 실행했다. 두 호출 모두 성공했고 원본 1건에서 기록 2건이 생성됐다. 직렬 재전송 차단 테스트가 통과해도 이 경쟁은 남는다.
- **고치는 방안:** `BEGIN IMMEDIATE` 이후 묶음·행·마감·활성 상태를 다시 읽고 보낸 상태를 원자적으로 갱신한다. 원본 행 ID를 기록에 연결하고 유일성 제약으로 중복을 막는 것도 권고한다. 마감 검사 뒤 다른 스레드가 마감하는 일반 기록 수정 경로도 동일 원칙으로 보완한다. UI 버튼 잠금은 보조 수단이다.
- **요구사항:** J12, J18.

### H08. 늦은 학생 조회 응답으로 A의 화면 내용을 B에게 저장할 수 있음

- **우선순위 / 분류:** 높음 / 자료·버그
- **위치:** `app/web/app.js:1220`, `app/web/app.js:1239`, `app/web/app.js:1509`

### H13. SHA-256이 없는 업데이트도 적용 경로로 통과함

- **우선순위 / 분류:** 높음 / 보안
- **위치:** `app/updater.py:58`, `app/updater.py:69`, `app/updater.py:74`, `app/updater.py:96`
- **문제:** 해시 비교가 `if info.get("sha256")` 조건에 묶여 있다. Release 자산의 digest가 비어 있으면 내려받은 실행 파일의 검증을 생략한다. `.exe`라는 확장자만으로 첫 자산을 고르는 것도 적용 파일 식별을 약하게 한다.

- **고치는 방안:** 예상 파일명을 명시하고 64자리 SHA-256이 없거나 잘못됐으면 자동 적용을 중단한다. 다운로드 후 필수 해시 검증과 크기 확인을 수행한다. 최초 URL의 저장소 prefix 제한은 유지하고 리다이렉트 시 허용되는 HTTPS 자산 호스트도 명시적으로 검사한다. 해시는 GitHub의 신뢰된 Release 메타데이터에서 얻는 구조이며 별도 제작자 서명을 대체하지는 않는다.
- **요구사항/요청 범위:** A3, J19, 업데이트 무결성 검토.

- **위치:** `app/export.py:25`, `app/export.py:35`, `app/export.py:53`

- **재현·근거 — 재현 확인:** `=1+1` 본문을 내보내고 다시 열었더니 `D2.data_type == "f"`였다. 33,000자 본문은 32,767자로 줄었다. Excel에서 외부 통신 함수나 링크를 실제 실행하지는 않았다. 일반 목표 분량의 최종안은 긴 셀 한도에 도달하지 않는다.

J12의 마감 후 태그 변경 금지와 J22의 전체 태그 이름 변경·사용 중 삭제가 충돌할 여지도 있다. 현재 태그 관리의 이름 변경/삭제는 마감 기록에도 반영된다(`app/records.py:114`, `app/records.py:123`). **태그 사전 관리의 전역 반영은 예외인지** 결정하고 문구와 검증을 맞추는 것이 좋다. 이 부분은 확정 규칙 간 해석 문제이므로 잠금 결함으로 단정하지 않았다.

## 5. 개인정보·외부 호출 경로 점검

| AI 경로 | 실제 전송 재료 | 판정 |
|---|---|---|
| 인박스 정제 `api.py:1025` | 행 content + 항목 정제 지침/예시 | 구조화된 학번/이름 필드는 별도 전송하지 않지만 OCR 잔류 H01 |
| 기록 정제/기작성문 다듬기 `api.py:609` | 기록 content + 지침/예시 | DB의 학번/이름을 붙이지 않음. 들어온 본문은 그대로 전달 |
| 여러 기록 종합 `api.py:632` | 선택 기록 본문·비율 + 지침/예시·선택 성취기준/수준 | 학생 식별 필드 대신 기록 순번을 사용. OCR 원문 잔류는 그대로 전파 |
| 기준만 생성 `api.py:682` | 기준 텍스트·성취수준 + 지침/예시·기록 없음 안내 | 학번/이름을 별도 삽입하지 않음 |
| 최종안 다듬기 `api.py:730` | 저장된 final.text + 지침/예시 | 식별 필드를 붙이지 않음. 미저장 화면 글과는 다를 수 있음(H12) |

붙여넣기/xlsx의 여러 학생 경로는 선택한 학번·이름 열을 내용 열에서 제외한다(`app/inbox.py:137`, `app/api.py:804`). 한 학생 모드의 입력 셀과 성취기준·프롬프트·예시는 자유 텍스트로 전달된다. 따라서 사용자가 본문이나 예시에 이름을 직접 넣는 경우까지 차단하는 구현은 아니다. 이는 최신 B3에서 본문 치환·미리보기를 하지 않기로 한 결정과 구분했다. 안내의 ‘내용만 전송’이 모든 자유 텍스트의 자동 비식별화를 보증하는 말로 읽히지 않도록 표현을 명확히 하는 것이 좋다.

추가 확인:

- OpenRouter의 privacy 옵션은 `data_collection=deny`, `zdr=true`로 구성되며 호출 오류 시 자동 해제하는 코드는 찾지 못했다. 다만 H10 때문에 설정 저장 자체가 누락될 수 있다.
- CLOVA에는 PDF 이미지와 설정 키를 전송한다. 안내가 존재하고 네트워크 예외는 예외 클래스명으로 축약한다. 입력 URL에 HTTPS/허용 호스트 검증은 없으므로 잘못된 URL로 키·자료가 전송되지 않게 검증을 보완할 수 있다(`app/ocr.py:48`). 실제 외부 호출은 하지 않았다.
- 키 입력칸은 password이고 [표시] 동작이 명시적이다. 키를 별도 로그에 직접 쓰는 코드는 찾지 못했다. 일반 예외·원격 오류의 비밀값 가림은 L01의 제한이 있다.
- 외부 링크는 `https://`로 시작할 때만 기본 브라우저로 연다(`app/api.py:146`). `javascript:`나 `file:`을 허용하는 경로는 찾지 못했다. 호스트 allowlist는 없으나 정적 도움말 링크 외에 일반 자료를 HTML 링크로 렌더링하지 않는 점도 확인했다. 링크를 실제 열지는 않았다.
- 일반 학생 자료·AI 응답은 주로 `textContent`/텍스트 노드로 출력한다. 원본 자료를 곧바로 innerHTML로 넣는 명백한 경로는 찾지 못했다. 로컬 정적 안내와 앱 정보는 HTML 출력이 있으므로 향후 외부 HTML·Markdown 표시 기능 추가 시 별도 검토가 필요하다.

## 7. 확인하지 못한 범위

- Windows exe의 실제 실행, 학교 PC 권한·보안 프로그램, WebView2 설치 상태, 1366×768/125% 및 세로 화면의 실제 배치. CSS 판정은 소스 기준이다.
- pywebview 전체 화면을 이용한 클릭·키보드·IME·접근성 시험. JS 재현은 실제 함수 코드를 사용한 모의 상태/DOM 시험이다. Chrome이나 다른 브라우저를 실행하지 않았다.
- 실제 OpenRouter/CLOVA/GitHub 응답, 모델 품질·요금·제공자 정책, 외부 링크, API 키의 유효성. 모든 재현은 합성 자료·모의 응답·로컬 파일 기준이다.
- Windows 프로세스 두 개를 실제로 띄운 시험. 단일 인스턴스 제약 부재는 코드로 확인했고, 중복 보내기 경쟁은 동일 DB의 두 스레드로 재현했다.
- Windows의 실제 exe 교체·재실행·롤백 및 CI 성공 이력. 워크플로의 자체 시험/교체 시험 정의는 읽었지만 GitHub에 접속하거나 push/워크플로 실행을 하지 않았다.
- NEIS에 실제 붙여넣기, Excel 수식 실행·외부 연결, Windows 네이티브 클립보드와 한글 경로 파일 대화상자. 임시 DB·스캔 폴더·자료 파일의 한글 이름은 로컬 백엔드 검증에서 사용됐다.
- 전원 차단·디스크 가득 참·부분 파일 손상·수십만 셀·압축 폭탄·최대 크기 PDF 등 실장애/부하 시험. 복원의 원자성·자원 한도 관련 지적은 코드 경로 기반이다.
- 실제 학생 자료, 기존 운영 데이터 마이그레이션, 모든 오래된 DB 스키마 조합. 실제 개인정보는 읽거나 전송하지 않았다.
- 사용자가 최종 승인한 기본 프롬프트 예시의 존재와 실제 교사 사용자 테스트. 현재 저장소 문서와 구현만으로 판단했다.
