# ‘태그별 기록’ 구현 UX 검토

- 검토일: 2026-11-10
- 기준: `feature/v0.15`, HEAD `9680e3d` 및 검토 당시 미커밋 구현. 줄 번호는 현재 작업 트리 기준이다. 검토 시작부터 있던 변경은 보존했다.
- 참고: `docs/design/TAG_VIEW.md`와 맨 아래 결정, 지난 `codex_tagview_design.md` T01~T17, 지정 화면·API·저장 코드, `tests/test_tag_view.py`.
- 방법: 정적 검토, 임시 자료 폴더의 Python API 테스트, 실제 JS 함수를 추출한 Node 모의 실행. 모의 실행은 최소한의 가짜 DOM·지연 API 응답을 사용했으며 브라우저 렌더링 검증이 아니다.

## 전체 판단

설계 결정의 큰 방향은 구현됐다. 학년-반과 수업의 조회 범위를 나누고, 담당·항목별 출처와 상태를 붙였으며, 마감·비활성·보관 학년도는 화면에서 읽기 전용으로 처리한다. 단일 태그, 학년-반→학생→담당 순서, 100건 표시와 잘림 안내, 중립 선택색, 최종안 자동 반영이 아니라는 설명도 적절하다.

그러나 **안전하게 바로 고치기**는 아직 보완이 필요하다. 기본 테스트는 통과하지만, 조회 응답 순서·저장 응답 병합·되돌리기 도중 입력·충돌 복구에서 글이나 태그를 잃을 수 있다. 상 6건(W01~W05·W12)을 먼저 해결하고, 접기·되돌린 메타정보·최종안 재검토 표시를 확인할 것을 권한다. 아래는 총 16건이다.

심각도: **상**=입력·태그 손실/덮어쓰기 또는 충돌 후 정상 작업 복구 차단, **중**=상태·대상·복구 범위 오인과 주요 작업 방해, **하**=보조 탐색·접근성 개선. 재현은 로컬 API·모의 실행으로 확인한 결과와 코드상 확인 절차를 구분했다.

## 상세 검토

### W01. 저장 응답에 다른 필드의 변경이 섞이면 다음 저장이 그 변경을 지움

- **심각도: 상**
- **문제:** `app/web/app.js:2650–2668`. 내용만 수정했어도 응답의 모든 필드를 `st.saved`에 반영한다. 그러나 `st.draft`는 이번 diff 필드만 갱신한다. 다른 경로에서 바뀐 태그·날짜·제목은 저장 기준에만 들어가고 초안은 옛값으로 남아, 앱이 이를 사용자의 추가 수정으로 오인한다. 다음 flush에서 새 값을 기대값으로 삼아 옛값을 덮으므로 expect도 보호하지 못한다.
- **재현 방법:** 기록 태그가 `[독서]`인 상태에서 내용을 고친다. 내용 저장 응답 전에 다른 경로에서 탐구 태그를 추가한다. 응답이 내용 수정과 `[독서, 탐구]`를 반환하게 한다. 실제 `tvSaveNow` 모의 실행 결과는 saved 태그 `[1,2]`, draft 태그 `[1]`, 다음 diff `{tag_ids:[1]}`였다. 이후 Ctrl+S/이동 저장이 탐구를 제거할 수 있다. 기존 `update_record`는 응답에 전체 현재 필드를 주므로 가능한 응답이다.
- **제안:** 응답을 반영할 때 각 필드의 기존 saved·요청 시점 draft·현재 draft를 비교한다. 사용자가 바꾸지 않은 필드는 새 서버값을 초안에도 반영하고, 저장 중 실제로 더 고친 필드만 유지한다. 서버값 갱신이 새 로컬 편집을 만들어내지 않아야 한다.

### W02. 늦은 조회 응답이 현재 태그·필터와 새 입력을 덮음

- **심각도: 상**
- **문제:** `app/web/app.js:2747–2758`, `2809–2823`. 조회 요청 번호·태그·필터·학년도 일치 확인 없이 도착한 응답마다 `TV.rec.clear()`로 초안과 복구 기준을 교체한다. 태그/조건을 바꾸는 동안 기존 기록도 편집 가능한 채 남는다. 저장 가드는 요청 시작 전에만 실행하므로 요청 뒤의 입력을 보호하지 못한다.
- **재현 방법:** 태그/필터 조회 A의 응답을 지연시키고 조회 B를 먼저 완료한다. B 결과에서 글을 입력한 뒤 A를 완료한다. 두 실제 `renderTagView` 호출의 응답을 역순으로 돌린 Node 모의 실행에서 `응답 대기 중 새 입력`이 사라지고 `원문`으로 바뀌었다. 조건 변경 한 번 뒤 응답을 기다리는 동안 옛 목록을 수정하는 경우도 같은 보호가 필요하다.
- **제안:** 요청 식별자와 태그·필터·학년도 스냅샷을 검증해 최신 응답만 적용한다. 조회 중에는 기존 결과 편집을 잠그거나 입력이 생긴 뒤에는 응답 적용을 보류한다. 초안 맵 교체 직전에 미저장/진행 작업을 다시 확인하고, 조회 실패 시 선택 조건과 실제 결과가 다른 채 남지 않게 한다.

### W03. 충돌 안내가 권하는 ‘새로 불러오기’가 같은 충돌 저장에 막힘

- **심각도: 상**
- **문제:** `records.py:565–571`, `app.js:2629–2636`, `2715–2718`, `4148`. 충돌 응답은 새로 불러오라고 안내하지만 버튼은 먼저 `leaveOk()`로 충돌한 초안을 다시 저장한다. expect가 여전히 옛값이어서 계속 실패한다. 행에는 다시 저장·내용 복사만 있고 로컬 초안 취소/서버 현재값 비교 경로가 없다. 메뉴 이동도 같은 실패에 막힌다.
- **재현 방법:** 태그 화면이 읽은 내용을 다른 API 경로에서 수정한 뒤 태그 화면의 옛 초안을 저장한다. 충돌을 확인하고 새로 불러오기·다른 메뉴 이동을 시도한다. 충돌 응답을 반환하는 실제 저장/flush 모의 실행은 `false`를 반환했다. 코드상 재조회는 실행되지 않는다. 현재 값으로 수동 복원하거나 초안을 버리고 닫는 등의 우회가 필요해진다.
- **제안:** 충돌을 일반 통신 실패와 구분한다. `내 수정 보관·복사 / 서버 내용과 비교 / 이 기록 초안 취소하고 다시 읽기`를 제공한다. 사용자가 명시적으로 포기한 초안만 저장 가드에서 제외한다. 다시 저장을 반복하는 것만으로 해결된다고 안내하지 않는다.

### W04. expect 검사와 쓰기가 분리돼 있어 동시 수정 보호가 완전하지 않음

- **심각도: 상**
- **문제:** `app/records.py:562–594`, `287–305`. 현재값을 읽고 expect/되돌리기 조건을 검사한 뒤 별도 트랜잭션에서 쓴다. 검사와 쓰기 사이에 다른 요청이 수정하면 검사는 통과했지만 다른 글을 덮을 수 있다. `YearDb.tx()` 잠금은 그 뒤 쓰기 구간만 보호한다. ‘화면을 연 뒤 바뀌면 덮지 않음’이라는 보장에 빈 구간이 있다.
- **재현 방법:** 임시 DB에서 expect 현재값을 읽는 직후 다른 `Records` 인스턴스가 `동시에 다른 곳에서 수정`을 저장하도록 끼워 넣고, 원래 저장을 계속했다. 거부되지 않고 `태그 화면의 수정`으로 덮였다. 이는 결정적으로 실행 순서를 만든 로컬 재현이며 실제 화면에서 동시 요청 빈도를 측정한 것은 아니다.
- **제안:** 현재값 확인·마감 검사·조건 검사·쓰기를 한 트랜잭션/동일 잠금 범위에서 수행한다. 또는 버전 조건을 포함한 UPDATE로 변경 행 수를 검사한다. 개별 저장과 되돌리기를 모두 같은 규칙으로 처리해야 한다.

### W05. 일괄 태그 되돌리기가 나중에 다시 붙인 태그까지 제거함

- **심각도: 상**
- **문제:** `records.py:250–275`, `app.js:3010–3014`. 처음 실제로 바뀐 쌍만 기억하는 것은 맞지만, undo는 마감·삭제·태그 존재만 확인하고 현재 작업 버전은 확인하지 않는다. 해당 관계가 그 후 다시 바뀌었어도 무조건 역연산한다. 최초부터 있던 태그를 보존하는 기본 테스트와는 다른 경우다.
- **재현 방법:** 없던 독서 태그를 일괄 추가해 pairs를 받는다. 이후 개별 수정 등 다른 경로에서 독서를 뺐다가 의도적으로 다시 붙인다. 최초 일괄 작업의 되돌리기를 실행한다. 임시 API 재현에서 `done=1, skipped=0`으로 성공하며 나중에 붙인 독서가 제거됐다. 제거 작업의 되돌리기 역시 이후 의도와 충돌할 수 있다.
- **제안:** 실행 후 해당 기록/태그 관계의 변경 버전을 보관하고 이후 다시 바뀐 것은 되돌리지 않는다. 단순 현재 포함 여부만 비교하면 제거→재추가를 구분할 수 없으므로 버전이나 작업 이력이 필요하다. 건너뛴 사유도 마감·삭제뿐 아니라 후속 변경까지 알려준다.

### W06. 앞 반의 접기 버튼이 마지막 반을 접음

- **심각도: 중**
- **문제:** `app.js:2878`, `2885–2892`. 각 제목의 클릭 함수가 반복문 밖의 공유 `clsBox`를 참조한다. 렌더링이 끝난 시점에는 마지막 반 상자이므로 앞 반 버튼도 마지막 상자를 바꾼다. 클릭 후 화살표와 `aria-expanded`도 갱신하지 않는다.
- **재현 방법:** 서로 다른 두 반 학생의 기록을 표시하고 첫 반의 접기 버튼을 누른다. 실제 `tvRenderMain` 모의 DOM 실행에서 첫 상자는 `tv-class`로 남고 두 번째가 `tv-class folded`가 됐다. 저장되는 fold 키는 첫 반이어서 다시 그리면 갑자기 다른 결과가 된다.
- **제안:** 클릭 함수가 해당 상자 인스턴스를 고정 참조하도록 한다. 상자·화살표·접힘 속성을 함께 갱신하고, 두 반 이상 및 저장된 접힘 상태에서 재조회한 경우를 확인한다.

### W07. 날짜·활동명을 되돌려도 화면 입력칸은 수정 후 값으로 남음

- **심각도: 중**
- **문제:** `app.js:2689–2696`, `2930–2948`, `2978`. 되돌리기는 saved/draft를 복원하지만 redraw는 본문·태그만 갱신한다. 메타 머리와 날짜·활동명 입력은 옛 UI 값이다. 사용자가 다음 날짜를 바꾸면 `upd()`가 남아 있던 활동명까지 draft에 다시 써서 방금 되돌린 값을 재저장할 수 있다.
- **재현 방법:** 활동명을 ‘이전 제목’→‘변경 제목’으로 저장하고 되돌린다. 모의 실행 결과 draft는 ‘이전 제목’이지만 머리는 `1회 · 변경 제목`, 입력칸도 ‘변경 제목’이었다. 그 상태에서 날짜를 바꿔 저장하면 활동명 재변경 위험이 있다.
- **제안:** 메타 머리·날짜·제목 컨트롤을 같은 상태에서 다시 동기화한다. 되돌리기 뒤 컨트롤 값을 확인하고 다음 메타 편집이 복원 결과를 출발점으로 쓰도록 한다.

### W08. 일괄 태그 처리만 현재 목록을 즉시 재조회하고 개별 복구 기준도 지움

- **심각도: 중**
- **문제:** `app.js:3005–3009`, `2755–2758`. 개별 칩 제거는 자리 유지인데 일괄 제거는 즉시 재조회한다. 현재 태그를 뺀 학생들이 곧바로 사라지고, 모든 기록의 `orig`도 초기화되어 이전 본문 수정의 되돌리기가 사라진다. 현재 태그 제거가 아닌 다른 태그 추가에도 같은 초기화가 발생한다. 토스트 되돌리기는 일괄 태그만 복구하며 9초 후 숨는다(`3852–3859`).
- **재현 방법:** 본문을 고쳐 개별 되돌리기가 생긴 뒤 같은 기록에 일괄 태그를 추가한다. 재조회 후 본문 되돌리기가 없다. 현재 선택 태그를 일괄 제거하면 ‘다음 조회 때 빠짐’ 표시 없이 학생 카드가 즉시 빠진다. 코드 경로 확인이다.
- **제안:** 실제 변경 쌍으로 화면 상태·집계를 부분 갱신하고 개별 orig를 보존한다. 일괄 제거도 개별 제거처럼 제외 예정 표시를 유지한다. 저장된 복구 기준을 언제 종료하는지 명시하고, 일괄 작업 결과·되돌리기는 사라지는 알림 외에 지속되는 위치를 제공한다.

### W09. 내용 저장 후 최종안 재검토 배지가 즉시 나타나지 않음

- **심각도: 중**
- **문제:** `app.js:2669`, `2709–2730`, `2906–2913`. 서버 stale 응답을 기록 객체에는 넣지만 담당 머리의 재검토 배지는 조회/전체 재렌더 때만 생성한다. 한 담당에 여러 기록이 있을 때 그 담당의 나머지 기록 상태도 함께 갱신하지 않는다. 도움말의 ‘최종안이 있으면 표시가 뜬다’와 다르다(`index.html:446`).
- **재현 방법:** 최종안이 있고 stale이 아닌 기록을 수정·저장한다. 서버 응답 stale=true를 반환한 모의 실행에서 객체는 true였지만 화면의 `.tv-stale` 배지는 0개였다. 새로 조회해야 나타난다.
- **제안:** 저장 성공 시 담당·항목·학생 키로 연결된 머리 표시를 갱신한다. 초록 ‘최종안 있음’은 유지하면서 노랑 재검토 배지를 추가한다. 저장 완료와 최종안 검토 완료는 별도임을 바로 알 수 있어야 한다.

### W10. 저장 중 더 입력해도 행에는 ‘저장됨’과 되돌리기가 표시됨

- **심각도: 중**
- **문제:** `app.js:2667–2679`, `2703–2722`, `2979–2981`. 저장 중 새 입력은 draft에 남기는 방향은 맞다. 그러나 응답 뒤에는 diff가 남아도 행을 무조건 saved로 표시한다. 상단은 ‘저장 전’인데 행은 ‘저장됨’이 된다. 페이지 추가 등으로 다시 그릴 때도 orig가 있으면 dirty 여부보다 저장됨을 우선한다. 실패 뒤 초안을 옛 saved 값으로 돌리면 failed 집계가 남을 수도 있다.
- **재현 방법:** 첫 문장을 blur 저장하고 응답 전 같은 칸에 두 번째 문장을 더 입력한다. 첫 응답을 완료하면 새 초안이 남아 있어도 `tvMark(st,'saved')`가 호출된다. 그 상태에서 다음 100건을 펼쳐도 저장 표시가 정확히 복원되는지 확인한다. 코드 경로 확인이다.
- **제안:** 응답 후·재렌더 때 상태를 `실패 / 저장 중 / draft≠saved / 저장 완료` 순으로 계산한다. 현재 보이는 모든 글이 저장된 경우에만 저장됨을 표시한다. 실패 사유·실패 해제도 실제 현재 초안 상태와 함께 관리한다.

### W11. 태그별 기록에서 학년도를 바꿔도 이전 학년도 화면이 남음

- **심각도: 중**
- **문제:** `app.js:269–287`, `2747–2749`, `4071–4075`. `reloadYear()`의 화면별 재조회 목록에 tagrec가 없다. 상단 학년도·ys만 바뀌고 이전 태그·기록·읽기 전용 여부·초안 맵은 남는다. TV의 학년도 초기화도 `renderTagView`를 다시 호출해야 실행된다.
- **재현 방법:** 임시 두 학년도를 준비해 태그별 기록을 표시한 채 학년도를 바꾼다. 호출 경로에는 tagrec 재조회가 없으므로 이전 기록 카드가 남는다. 실제 개발 서버 자료는 전환하지 않았으며 코드상 확인이다. 서버의 보관 학년도 쓰기 차단이 있으므로 이것만으로 다른 학년도 덮어쓰기가 발생했다고 단정하지 않는다.
- **제안:** 학년도 전환 시 tagrec를 명시적으로 초기화·재조회하고 로딩 동안 편집을 막는다. 모든 저장·되돌리기에 기대 학년도를 전달해 서버에서도 맞는지 확인한다. 이전 학년도 응답이 나중에 도착하는 경우는 W02의 검사로 함께 막는다.

### W12. 되돌리기 응답을 기다리는 동안 새로 쓴 글이 사라짐

- **심각도: 상**
- **문제:** `app.js:2682–2696`. 되돌리기는 저장 큐 완료만 기다리고 자기 작업을 큐/inflight에 등록하거나 편집을 잠그지 않는다. 응답 때 `st.draft={...st.saved}`로 통째로 교체한다. 대기 중 추가 입력·화면 이동과 충돌할 수 있다. 일괄 태그 작업·일괄 undo도 같은 공통 작업 가드에 등록되지 않아 W02/W08의 재조회와 겹칠 수 있다.
- **재현 방법:** 되돌릴 수 있는 기록에서 버튼을 누르고 API 응답을 지연시킨다. 그 사이 본문에 `되돌리기 응답 전에 새로 입력`을 적은 뒤 성공 응답을 준다. 실제 `tvUndo` 모의 실행에서 draft가 복원 응답의 `처음`으로 바뀌어 새 글이 사라졌다.
- **제안:** 되돌리기도 해당 기록의 변경 큐에 등록하고 처리 중에는 그 기록의 편집·중복 실행을 막는다. 이동 가드도 되돌리기·일괄 변경 작업 완료를 기다려야 한다. 편집을 허용한다면 요청 이후 새 입력을 별도 보존하고 덮어쓰지 않는다.

### W13. 다른 항목을 확인하고 돌아오면 작업 위치·복구 기준이 없어짐

- **심각도: 중**
- **문제:** `app.js:1581–1588`, `225–240`, `2747–2763`, `2913`. 링크가 담당·학생을 정확히 여는 것은 좋다. 다만 돌아오면 `renderTagView()`가 재조회하면서 orig를 지우고 keepScroll도 요청하지 않는다. 목표 기록 ID를 전달하지 않아 긴 항목별 기록에서는 해당 기록을 다시 찾아야 한다. 도움말은 되돌리기가 이 화면의 초기값으로 돌아간다고 설명하지만 필터 변경·왕복이 복구 기준을 종료하는 점은 명확하지 않다.
- **재현 방법:** 아래쪽 학생 기록을 수정한 뒤 그 항목에서 열기로 최종안을 확인하고 태그별 기록으로 돌아온다. 재조회 초기화 코드로 이전 개별 되돌리기가 사라진다. 실제 스크롤 복원 위치는 브라우저 미실행으로 실측하지 않았다.
- **제안:** 태그·필터·표시량·접힘·기록 앵커를 저장해 왕복 시 복원한다. 기록 ID로 항목별 화면의 해당 기록을 강조한다. orig를 재조회 후에도 안전하게 유지하거나, 복구 가능 범위가 조회 세션까지라는 점을 버튼/도움말에 정확히 명시한다.

### W14. 비활성·보관 읽기 전용도 마감 파랑으로 표시됨

- **심각도: 중**
- **문제:** `style.css:689`, `app.js:2737–2742`, `2972–2975`. `.tv-lock`은 이유와 관계없이 `--st-closed` 색이다. 마감이 아닌 비활성·보관 학년도도 파랑으로 보이므로 색만 보면 마감으로 오해한다. 다른 기록의 노랑 입력 중 배지와 파랑 잠금 문구가 같이 있을 수도 있다. 업무 상태 배지 자체는 공통 STATUS와 맞는다.
- **재현 방법:** 마감되지 않은 비활성 학생을 ‘비활성 포함’으로 표시하거나 보관 학년도 기록을 읽는다. `비활성 학생·읽기 전용` 또는 `보관 학년도라 읽기 전용` 문구가 동일 파랑 CSS를 받는다. 코드/CSS 대조 결과이며 실제 색 대비는 미측정이다.
- **제안:** 마감에만 파랑 ●를 사용하고 비활성·보관은 중립색과 잠금 기호·이유로 표시한다. 상태색, 선택색, 저장 상태는 현재처럼 구분하고 색 외 글자를 유지한다. 화면별 비교는 아래 표 참조.

### W15. 같은 문장의 바이트 수가 항목별 기록·내보내기와 다름

- **심각도: 중**
- **문제:** `app.js:2732–2735`의 새 `byteLen`은 비ASCII 문자를 UTF-8에 가까운 2/3바이트로 센다. 기존 `bytesOf`(`1460–1463`)와 서버 `app/textutil.py:15–17`는 한글 3, 그 외 1 규칙이다. 가운데점·번호 기호·한자·그리스 문자가 든 교과 기록에서 표시가 어긋난다. 저장 응답의 서버 bytes도 화면은 다시 draft의 byteLen으로 표시한다.
- **재현 방법:** 같은 문자열 `독서 · ①`을 두 함수에 넣었다. 기존/서버 규칙은 10B, 태그 화면은 13B다. 교사는 불필요하게 글을 줄이거나 다른 화면의 계산을 불신할 수 있다.
- **제안:** 별도 계산식을 추가하지 말고 공통 바이트 계산을 사용한다. 표시 화면·저장 응답·내보내기에서 같은 규칙으로 일치시킨다.

### W16. 키보드·좁은 창에서 편집 대상 문맥과 초점 안내가 부족함

- **심각도: 하**
- **문제:** `app.js:2928`, `2932`, `2959–2963`, `2919–2920`, `index.html:136`. 같은 학생의 여러 과목 글상자 접근성 이름은 모두 ‘학생명 기록 내용’이고 날짜·활동명·태그 선택에 담당 맥락이 없다. 다음 100건은 전체 본문을 재생성하므로 눌렀던 버튼의 초점도 사라질 수 있다. 좁은 창에서는 태그 목록을 숨기지만 빈 화면은 여전히 ‘왼쪽에서 태그를 고르세요’라고 안내한다(`2858`, `style.css:712–715`).
- **재현 방법:** 같은 학생의 두 과목 기록에서 생성되는 aria-label을 비교한다. 동일한 이름이다. 980px 이하에서는 상단 선택기를 쓰게 되는데 빈 안내는 왼쪽을 가리킨다. 실제 Tab·스크린리더·배율별 초점은 미검증이다.
- **제안:** 접근성 이름에 학생·담당·회차를 포함하고 검색 입력에도 명시적 이름을 준다. 다음 100건은 기존 DOM/초점을 보존하거나 새로 추가된 첫 기록으로 안전하게 이동시킨다. 빈 안내는 ‘태그를 고르세요’처럼 배치에 독립적으로 쓴다.

‘되돌리기’는 직전 한 번이 아니라 이 조회에서 최초 수정 전 필드값으로 돌아간다. 버튼과 도움말에 `이번 조회의 수정 전으로`처럼 실제 범위를 드러내는 편이 좋다. ‘저장 실패’도 통신 오류·충돌·마감됨·빈 내용 오류를 구분하고 각기 가능한 다음 행동을 보여줘야 한다. 복사 버튼은 `navigator.clipboard.writeText()` 성공을 기다리지 않고 성공 토스트를 띄우므로, pywebview의 실제 클립보드 지원·거부 시 메시지도 확인할 필요가 있다(`app.js:2718`). 실제 복사 실패를 재현한 것은 아니다.

## 검증 결과와 남은 실기 확인

`PYTHONDONTWRITEBYTECODE=1 .venv/bin/python -B tests/test_tag_view.py`는 **TAG VIEW OK**로 통과했다. 반·수업·담당·검색 필터, 기본 개별 저장/복구, expect 불일치 거부, 마감 기록 거부, 원래 있던 태그를 보존하는 기본 일괄 undo, 비활성 기본 제외가 포함된다. 화면 함수의 응답 순서·초안 병합·메타 재표시·접기 이벤트는 이 테스트 범위에 없다.

추가로 실제 JS 함수 추출 모의 실행에서 W01·W02·W03·W06·W07·W09·W12·W15를 확인했다. Python 임시 API/Records 실행으로 W04의 검사-쓰기 간 변경 주입, W05의 후속 태그 재추가 후 undo를 확인했다. 모든 데이터는 임시 폴더의 가상 기록이며, 개발 서버의 현재 자료를 시험용으로 수정하지 않았다.

많은 기록은 첫 100건만 그리지만 서버 `tag_view`는 해당 결과 전체 본문을 반환하고, 프런트는 전체를 TV.data·TV.rec에 보관한다(`records.py:321–405`, `app.js:2758`, `2863`). 따라서 ‘100건씩 표시’는 조회 전송량/메모리 제한이 아니다. 현재 규모에서 느리다고 측정한 것은 아니며, 출시 전 다음을 확인해야 한다.

- 101건·1000건 이상, 같은 학생의 100건 경계 분할, 긴 본문에서 조회 응답·저장·스크롤 반응
- 두 반 이상 접기, 접은 상태의 다음 100건 추가, 검색 결과 0건과 선택 태그 삭제
- 1366×768의 125%·150% 배율에서 필터 줄과 일괄 도구가 감긴 뒤 본문 편집 공간·sticky 머리 겹침
- 날짜·활동명·본문 입력 중 Ctrl+S, 태그 제거 직후 이동, 저장/undo 지연 중 반복 입력과 조건 변경
- 실제 충돌 뒤 복사·초안 포기·다시 읽기, 되돌리기 실패 뒤 재시도, 장문 오류의 표시 위치

이번 작업은 이 보고서만 추가했다. 기존 코드·테스트·설계안·다른 검토 문서는 수정하지 않았고 Chrome 실행·외부 전송·git commit/push도 하지 않았다.
